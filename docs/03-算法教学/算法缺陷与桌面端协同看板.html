🔴 冻结后新增 P0（2026-10-29）—— 本页统计口径不含此项

跨瓦片多边形既不按 core 裁剪、也不做全局融合：相邻瓦片各向外扩 128 px， 于是同一条 8.45 m 宽的重叠带被两块瓦片各算一遍。

  • 实测 1,449 对多边形相互重叠 / 80,123 m²（成对和，占总面积 18.3%， 这是上界：三块以上交叠处被重复计入）；
  • 按精确并集去重（按类 union）：需补种口径 323,652 → 276,219 m²（−14.7%）、 全部 7 类 −12.6%；其中连片空地 306,602 → 259,452 m²（−15.4%）；
  • 融合后块数：连片空地 474 → 230（−51%）、道路 180 → 94（−48%）、 确定需补种 751 → 485（−35%）；
  • 后果：需补种面积 / 占园比例 / 块数 / 面积折算株数系统性偏大， 而放样点数（3,691）不受影响（按 cm 级坐标去重）。

这一项不属于"判得准不准"，属于"算了两遍"，优先级高于本页所有条目， 且应在 150 块真值打标之前修复 —— 否则真值验的是一份口径已偏的底稿。

💡 为什么「先冻结算法、转向桌面端」是对的

剩余缺陷里最难缠的三个 —— 未开发林掩膜阈值敏感（4%~26% 摇摆）、 跨道路网格相位重置（全图对齐率仅 46%）、少量高草/幼树与硬化路口误判 —— 一旦桌面端上线「Step 2 用户圈选 Target Block」与 「Step 4 交互式增删多边形」，就在产品交互层被直接吸收：圈外野林根本不进管线，误判由用户一键删掉。 解冻后再按下方清单逐条升级底层算法即可。

⚠️ 两处必须纠正的对外说法（来自外部技术方案的建议）

1. 前端框架是 React，不是 Vue 3。 项目 docs/01-需求与架构/架构方案.html 已冻结技术栈： Tauri v2 + React 18 + TS + MapLibre GL 4；文件树、依赖清单、任务分解（T01–T05） 全部按 React 写好。绘图库用 Terra Draw（Leaflet-Geoman 只支持 Leaflet，不能用）。

2. 算法主链路走 stdio NDJSON sidecar，不是 FastAPI HTTP 微服务。 docs/01-需求与架构/推理服务契约.md 已冻结并实现（契约测试 95/95）。 FastAPI 方案要重新设计契约、管端口与进程生命周期、额外引入 3 个依赖，没有收益。 唯一的 HTTP 例外是瓦片服务（浏览器必须能 <img src> 取图）。

完整裁定见 docs/01-需求与架构/桌面端交互需求与实现映射.md。

🔍 根因与现象

在 1.2 m ≤ CHM < 5.2 m 且高绿度（ExG≥60）的区间，算法一律判"非树 → 需补种"。 但这一段里既可能有要清芭补种的高大杂草 / 野生灌木，也可能有已种下 2~4 年、 高 2~4 m 的幼龄油棕（不该重复补种）。

更麻烦的是：DSM高程辅助检测方案.html 里规划的「低矮植被」独立类别 代码中从未落地，而该方案"草 0.3~1.5 m vs 油棕 ≥4 m 一刀切开"的假设 已被本项目自己的实测否定（草地真值点 CHM 中位 3.05 m，被 DSM 平滑"渗高"）。

🖥️ 桌面端过渡方案

用户在桌面端知道哪个区块刚种了小苗。用 图层过滤 + 框选删除， 一键删掉已知幼龄区上的误报空地。

更根本的做法已在 PRD 里记下：给多边形加一个「人工确认」状态字段 （可导入补种计划表），算法只负责"哪里可疑"——因为"这块地什么时候推的、种没种" 本质是非影像信息。

🛠️ 解冻后修复方向

  • 在 1.2~5.2 m + 高 ExG 区加二级分类：幼龄油棕的放射状纹理 （6 方向 Gabor）+ 是否落在 8.35 m 种植格点上 → 剥离为 young_palm；
  • ⚠️ 但要注意：单期影像做不到"幼树 vs 高草"的语义区分， 需要多时相（同一地块两期对比）。不要在这上面继续堆特征工程。

📌 证据

probe_ambiguous.py：明确裸地 158,146 m²（37.5%，铁定要补）； 绿色中高植被 99,486 m²（23.6%，业务判断）。

P0 · 外部模型强耦合 D2　51% 的「非树」判定完全依赖大疆域外果树分割（segment.tif）
214,827 m²（占全幅有效区 16.7%）

🔍 根因与现象

在 1.2 ≤ CHM < 5.2 m 区间，CHM 既不触发救援也不触发否决， 51% 的非树判定完全由 segment.tif == other 决定。

而大疆智图果树模型只支持柑橘/荔枝/香蕉等 6 类果树，油棕属于域外推断； 若未来航拍未跑大疆果树分析（缺 segment.tif），F1 融合规则就失去光学主腿。 另有 segment.tif 不含内嵌 CRS（靠代码硬编码 EPSG:4326 兜底）， 换数据源可能静默错位。

🖥️ 桌面端能做什么（只能缓解，不能根治）

导入时校验工程目录是否含 segment.tif：有 → F1 高精度管线； 没有 → 明确提示并降级为「CHM + 局部归一化 ExG」备用管线（而不是静默出错）。

🛠️ 解冻后修复方向

  • 用当前 F1 高置信区做伪标签（CHM≥5.2 且 seg==tree 为正， CHM<1.2 且 seg==other 为负），训练超轻量本地分割头 （SegFormer-B0 / YOLOv11n-seg），导出 ONNX 供桌面端调用，摆脱对 segment.tif 的依赖；
  • 同时给 segment.tif 加 CRS 对齐校验 + 明确报错。

📌 证据

probe_chm_artifact.py：非树判据来源分工表 —— 51% 靠 seg、约 4% 靠 CHM 否决。 属底层输入依赖，桌面端不能化解。

P1 · 阈值泛化脆弱 桌面端可开参数滑块 D3　CHM 融合阈值（5.2 m / 1.2 m）对树龄与 DSM 平滑度高度敏感
CHM 阈值每变 ±1.0 m → ±30,400 m² 翻转

🔍 根因与现象

大疆 gsddsm.tif 经过强平滑，冠层高度被系统性低估约 40% （真树 8~15 m，CHM 读数 5~9 m）。当前 5.20 m / 1.20 m 是在单一成熟园区按 仅 5 个真值点标定的。换到幼龄林园区或用未平滑的精细 DSM， 固定阈值会大面积漏救或误砍。

🖥️ 桌面端过渡方案

在「高级设置」暴露 chm_rescue_m（默认 5.2）与 chm_veto_m（默认 1.2） 两个滑块，或给「幼龄林 / 中龄林 / 成熟林」三档预设。这正是 sidecar 契约已支持的用户可配参数。

🛠️ 解冻后修复方向

  • 按 Target Block 统计有效 CHM 的双峰直方图（地面峰 vs 冠层峰）；
  • 用双高斯混合模型（GMM）或分位数自动标定该区块的 T_rescue / T_veto， 实现零人工调参的跨园区自适应。必须先做 A/B 验证，不可直接上线。

📌 证据

probe_dji_chm.py 的阈值敏感性扫描（±1 m ≈ ±3.0 万 m²）。

P1 · 网格相位与残树 圈选区块可大幅缓解 D4　全图共用单一网格原点对齐率仅 46%，且连片空地内包住 558 个存活树心
3 m 容差：全局 46.7%（≈随机 45.7%）· 局部 54.8%　｜　1 m 容差：5.1% → 7.3%

🔍 根因与现象

① 相位不连续：株距（8.45 m）与方位角（0.67°）已完全锁定， 但不同种植区块跨过林道 / 水沟后，种树起点相位会重置。全图共用一个原点时， 对齐率仅 ~46.7% —— 与二维随机基准 45.7% 几乎相同 （随机基准 = π·3²/61.836，单株占 61.836 m²），即全局网格与真实株位毫无相关性。

② 大斑块内含孤立残树（2026-10-17 重测）：558 个树心落在空地多边形内 （占全部 15,190 个树心的 3.7%），其中 490 个落在 open_patch。 不过方位已对：空地落在树心 ≤2 m 内的面积只有 2.1%，而全园自然基准是 14.5% —— 空地确实避开了树，这 558 个是零星漏网。

🖥️ 桌面端过渡方案

用户按单个 Target Block 圈选检测时，范围通常只有 200~400 m， 天然消除跨区块相位跳变。且点「估算棵数」时可直接扣减多边形内的存活树心。

🛠️ 解冻后修复方向 —— 实测后已决定不做（2026-10-17）

② 残树挖孔仍值得做（成本低、语义清晰）：对落入 open_patch 的孤立高置信树心做半径 2.5 m 布尔挖孔（Interior Ring），排坑时避开残树。

① 局域相位拟合：评估后放弃。实测把 300 m 窗口各自拟合相位后， 对齐率只从 5.1% 提到 7.3%（1 m 容差）/ 46.7% 到 54.8%（3 m 容差）—— 仅略高于随机。两个物理死限决定了搬动相位救不回来：

  • 树心本身抖动：DJI 树心 σ≈1.8 m，即使网格 100% 完美， 「≤1 m」的理论上限也只有 14.3%；
  • 株距拍频漂移：全局 8.45 m 与真实 NND 8.25 m 差 0.2 m， 在 300 m（约 36 棵）内累积漂移 ≈7 m，超过半个周期。

⚠️ 口径提醒：早期写过的「局部细扫 79.5%~97.3%」是特定小窗口 + 0.5°×8 相位网格搜索取最优 的结果，2026-10-17 用统一口径（全 20 个窗口、圆均值拟合）复现不出来， 不要当作普遍可达水平。

业务上也不需要：open_patch 是空地，原树已死，新苗按标准株行距铺点即可 （间距对、不侵到存活树冠下即可），不宣称「复现原株位」； vacant_slot 用质心，不受影响。

📌 证据（本次重跑 probe_gaps_truth2.py）

树心 15,190 → 落在空地内 558 个（3.7%）； 距树心 ≤2 m 面积 6,774 m²（2.1%）、≤3 m 6.2%、≤5 m 34.9%。

口径说明：更早曾用"274 个多边形内含树心（涉及 228,838 m²）"表述， 那是按多边形计数且"含 1 个即算"的严口径（对大连片块偏严）；本次改为按树心计数， 更可直接复核。

P1 · 边界掩膜敏感 桌面端圈选后彻底消失 D5　自动「未开发林掩膜」对网格尺度与阈值极敏感
不同参数下影响需补种面积在 4% ~ 26% 间摇摆

🔍 根因与现象

build_forest_mask.py 靠 50 m / 100 m 网格统计树心密度与规律性。问题有三：

  • 林缘交界处有明显 50 m 网格台阶锯齿；
  • 50 m 小网格（0.25 ha）低密度下有"小样本分母效应" —— 碰巧一对树间距 8 m 就能得到 25%~50% 的规律性得分；
  • 极易把刚推平清芭的待种地（树心密度 0）与原始野林混淆 —— 这正是 10-16 绿度闸门要修的那个坑。

另外 output/forest-mask-争议区.geojson 里还有 16 块 / 4.08 ha "真·模糊地带"，多特征指纹比对结果不干净（密度像森林、CHM 像种植区）。

🖥️ 桌面端直接根治

这项缺陷在桌面端上线后基本消失：Step 2 让用户沿目标区块的林道画框， 框外原始森林根本不进管线，不再需要自动猜边界。

届时 build_forest_mask.py 降级为"无 ROI 时的批处理兜底工具"。

🛠️ 解冻后修复方向

  • 桌面端管线用用户绘制的 roi 替代 forest-mask；
  • 保留掩膜工具仅作命令行全图模式的参考；
  • 若要继续自动判断，需引入标注验证集（当前 0 个标注样本， active_learning.py 已实现但从未运行）。

📌 证据

掩膜多参数对比实测区间 4%~26%；争议区 16 块 / 4.08 ha。 另有约 9,155 m² 落在 CHM_P90>13 的疑似 DSM 伪影区， 正确性不可验证。

P2 · 语义噪声 桌面端默认不显示，无感 D6　建筑门槛下调至 25 m² 后，部分「加宽硬化路口」被标为办公区
对需补种面积影响 0 m²，仅不可种植子类间语义混叠

🔍 根因与现象

Stage 14 为抓出 25~400 m² 的水塘泵房与化肥棚，把亮白低饱和（fill ≥ 0.30） 的 office 面积门槛从 400 m² 降到 25 m²。副作用是部分局部加宽 （约 10×5 m）、长宽比不够细长的白色砂石路口通过了 fill 判据， 被归入 office（现 82 块 / 7,235 m²）。

已裁图目视确认：这些新"办公区"里确实有硬化路口，不是建筑。

🖥️ 桌面端过渡方案

业务上完全无害：road 与 office 同属"不可种植"背景层， 桌面端默认只勾选「可种植（连片空地 / 株位空缺）」。 也可把 office 的前端标签显示为更准确的「建筑与硬化设施」。

🛠️ 解冻后修复方向

  • 加一条拓扑 + 高度规则：25~150 m² 的 office 若与 road 相接 （Touches / Intersects）且内部 CHM_P90 < 0.8 m（无房顶高度）， 则并回 road；
  • 或新增独立的 hard_surface（硬化地面）类别，语义更干净。

📌 证据

office 检出量 4 块 / 2,597 m² → 82 块 / 7,235 m²（修复收益 +4,638 m² 正确剔除）； 新检出中 93.9% 落在"亮白低饱和"掩膜内（标签自洽）。

P2 · 工程与性能债 D7　单进程跑批 1,048 秒、DSM 垂直尖峰伪影、遗留硬编码与退役模块
全量 528 瓦片 / 1,048.2 秒（串行）· 矢量化损耗 5.2%

🔍 逐项清单

  • 单进程串行：528 瓦片循环处理，本机 1,048.2 秒、公司机约 1,973 秒。 瓦片之间完全独立，多进程是"12 分钟目标"唯一现实路径（4 核可望 3~4×）；
  • DSM 垂直尖峰伪影：15 个健康油棕区块 CHM_P90 达 14.08~29.99 m（密度 72~163 株/ha、规律性最高 68% → 不可能是野生林）。 结论是"伪影叠在真树上"，因此漏检上限仅 6,420 m²， 但也意味着 CHM 不能用于精细高度分层；
  • 概览图只支持 4 类：visualize_full.py 的 CLASS_ORDER 缺 road/water/office/undeveloped，与 8 类交付包不一致；
  • 硬编码机器路径：build_forest_mask.py 的 --tree-info/--ortho 默认 D:\WGR\...； active_learning.py 的 IMG_DEFAULT = D:/WGR/WGR17.tif → 换机器直接报错；
  • 死参数：--unplantable-overlap 已失效（仅保留兼容）， 契约与 CLI 里仍暴露，容易误导；
  • 退役模块未标注：有 CHM/segment 时草地回检整链自动跳过 （属合理降级设计），但 10-13/14 那套判据实际已"退役"，文档需写清， 避免后人误以为它在起作用。

P2 · 工程与协同债 桌面端可绕过 ✅ 已修（94f1aab） D8　显式 --gaps 被「更新的残留文件」顶掉 → 网格串批次、点位全偏
要素数相同也可能点位全错：3,691 → 3,713 点（块数不变）

🔍 根因与现象

TileServer._pick_gaps() 原规则是「取 mtime 更新的那个」：

best = --gaps 指定的文件（若存在）
found = 扫目录 + 名字含 gaps + 取最新
if found 且 mtime(found) > mtime(best): best = found　← 显式指定的被盖掉

后果：同目录里只要有一个比它更新的 *gaps*.geojson， --gaps 指向的文件就永远读不到。而数据目录在真实使用中必然 累积多轮检测产物 —— 本仓库开发态就有 20 个匹配 *gaps*.geojson 的文件，最新的几份是只有 12 / 12 / 8 / 14 块的小样本残留。 而且不报任何错。

2026-10-19 冻结态校验实测：自动发现命中了一份 639 要素 / 6 类的 试验残留（具体文件名以脚本输出为准），导出得 19 文件 / 919 点； 正确结果应是 21 文件 / 3,691 点（wgr17-final-gaps.geojson， 1,726 要素 / 8 类）。

★ 真正的危害：网格串批次（比块数不对严重得多）

/export 里要素来自前端 POST，但 planting_grid 取自 current_gaps()（同一个"当前生效文件"）。 一旦发现到另一批文件：

要素网格（来自另一批）结果
正常1,726 origin_x=158.95 / pitch=8.453,691 点
串了批1,726 origin_x=159.32 / pitch=8.353,713 点

要素数一模一样、类别数一模一样、报告看起来完全正常， 但每一株的点位坐标都按错的网格结算了 —— 到场就挖错地方。 用户看不出来，这是它最危险的地方。

🛠️ 修法：区分「用户指定的时刻」与「文件的 mtime」

关键认识：这两件事不一样，不能直接拿 mtime 比大小。 在 __init__ 记一次"用户指定时刻"，之后只允许比它更新的文件接管。

self.gaps_explicit_at_ns = int(time.time()*1e9) if gaps is not None else None

if best is None: take = True
elif gaps_explicit_at_ns is not None: take = mtime(found) > gaps_explicit_at_ns
else: take = mtime(found) > mtime(best)

⚠️ 时间戳绝不能记在 _pick_gaps() 里 —— 它每个请求都调， 那样"启动时刻"永远等于"现在"，mtime > now 恒假 → 等于把「检测完自动刷新」（坑 42）彻底弄回去。

不需要动 Rust：用户指定的时机恰好就是 set_data_paths 重启服务之时。

📌 验证证据

选择逻辑（regress_gaps_selection.py，秒级，全绿）： 同一实例依次读到 3 / 7 / 11（原地覆盖与出现更新文件都能刷新）； 显式文件 mtime 调旧后仍胜出（读到 1,726）； 启动后新写的文件能接管；名字不含 gaps 的 geojson 不被误选。

端到端（e2e_export_bundle.py）：1,726 要素 / 8 类 / 21 文件 / 3,691 点 / 报告含 3,691； 换样本后 origin_x_m 跟着变成 159.3191（用户看到哪份就按哪份放样）。

机制说明（export_grid_ab.py）：同一批 1,726 要素 只换网格 → 点数在 3,656 ~ 3,713 变动、首点坐标同步漂移 （111.20402232, 1.19012672 → 111.20412956, 1.19002759）。

契约测试保持 95/95。
