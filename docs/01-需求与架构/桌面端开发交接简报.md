|---|---|---|
| 端口 | 不占端口 | 需占端口，可能被防火墙/杀软拦、被其它程序抢占 |

| 进度事件 | stdout 逐行 NDJSON，天然流式 | 需额外 SSE / WebSocket |

| 安全面 | 仅本机进程管道 | 暴露本机 HTTP 端口 |

## 1. 项目一句话

油棕种植园（**不是普通森林**）空地智能检测。输入 = 无人机正射影像（+ 可选 DSM / 语义分割），
输出 = 全园需补种空地的矢量图盘（GeoJSON / Shapefile / KML），供现场补种作业使用。
最终形态是 Tauri v2 桌面应用，当前算法层已完成并进入维护冻结。

**已实测的交付基线**（本机，528 瓦片，1,048.2 秒）：

| 指标 | 数值 |
|---|---|
| 确定需补种 | **702 块 / 309,143 m²**（占园区 13.49%） |
| 待复核（不确定） | 465 块 / 40,593 m² |
| 不计入（林间空隙） | 251 块 / 13,277 m² |
| 不可种植 | 道路 180/34,357 · 水体 21/9,711 · 办公 82/7,235 · 非种植区 25/20,412 |
| 交付包 | 1,726 要素 / 8 类 |
| 影像 | `drone data/WGR17-002.tif`：47,130×44,686 px · EPSG:4326 · 0.033 m/px · 4 波段 |

**注意**：KML/ROI 裁剪**在算法侧尚不存在**（`process_image.py` 的 `used_kml` 是硬编码 `False`，
sidecar 收到 `kml` 只发 `W1002` 告警后忽略）。这是桌面端必需的前置功能，见 §8。

## 3. 契约 A：算法主链路（stdio NDJSON sidecar）

**这是唯一允许触发算法的方式。**

### 3.1 宿主如何调用

```bash
# 方式 A：命令行参数
python scripts/sidecar.py --params-json '{"input":"D:/WGR/WGR17.tif","job":"wgr17-full"}'

# 方式 B：stdin（推荐 Tauri 用这个 —— 参数可能很长）
echo '{"input":"..."}' | python scripts/sidecar.py --params-stdin --params-json -

# 方式 C：参数文件
python scripts/sidecar.py --params-file job.json

# 自检（不跑算法，只验证事件通道）
python scripts/sidecar.py --self-test
```

### 3.2 事件流（宿主按行读 stdout 解析）

| 事件 | 时机 | 关键字段 |
|---|---|---|
| `started` | 进程启动 | `sidecar_version` |
| `progress` | 每 N 个瓦片 | 当前阶段 / 完成数 / 总数 / 耗时 |
| `stage` | 阶段切换 | 阶段名（导入 / 处理 / 合并 / 导出） |
| `warning` | 可继续的问题 | `code`（如 `W1002`）/ `message` |
| `result` | 成功结束 | `summary` / 输出文件路径 |
| `error` | 失败 | `code` / `message` / `traceback` |

**硬约定**：`stdout` **只允许 NDJSON**（人类日志走 `stderr`）。
`error` 事件必须在进程退出**前**写完并 flush，否则宿主拿不到失败原因。

## 4. 契约 B：唯一 HTTP 服务（瓦片）

`scripts/tile_server.py`，默认 `127.0.0.1:8765`。

| 端点 | 方法 | 返回 |
|---|---|---|
| `/meta` | GET | 影像元数据：`width/height/crs/res_m/bounds_wgs84/center/zoom/has_overviews/tile_url` |
| `/tiles/{z}/{x}/{y}.png` | GET | XYZ 瓦片（Web Mercator，256×256 PNG） |
| `/gaps` | GET | 最近一次检测结果 GeoJSON |
| `/export` | POST | 把前端编辑后的要素导出为 geojson / csv / kml |
| `/detect` | POST | **故意返回 501** —— 检测不由本服务提供，见 §3 |

启动：

```bash
# 首次建议加 --build-overviews（一次性，会就地修改影像，见 §10 坑 3）
.venv/Scripts/python.exe scripts/tile_server.py --build-overviews

# 换影像 / 换端口
.venv/Scripts/python.exe scripts/tile_server.py --source "drone data/WGR17-002.tif" --port 8765
```

**实测性能**（建金字塔后）：z=13 约 700 ms · z=15 约 838 ms · z=17 约 775 ms。

## 9. 八个必踩的坑（全部实测踩过并已修，附错误原文）

> 这一节是本项目最省时间的地方。请外部协作方**逐条对照**，不要重新踩一遍。

### 坑 1 · `Window.intersection` 无交集时抛异常

```text
rasterio.errors.WindowError: Intersection is empty Window(col_off=-28767472, ...)
```

`rasterio.windows.Window.intersection` **不是返回空窗口，而是抛 `WindowError`**。
低缩放级与园区外的瓦片必然走到这里 → 每个请求都抛栈。
**修法**：捕获异常后返回透明瓦片。

### 坑 2 · 波段索引别把 Alpha 算进去

本影像 **4 波段**（第 4 波段恒 255 = Alpha）。把 4 个波段送进目标是 3 波段的
`reproject` 会直接报错 → 瓦片全黑。
**修法**：只取 `[1, 2, 3]`。

### 坑 3 · 影像没有金字塔，低缩放级瓦片极慢

`overviews` 为空 → 低缩放级瓦片窗口覆盖大半个影像，GDAL 只能按全分辨率读：
**实测 z=13 约 104 秒、z=15 约 35 秒一张**。
**修法**：`--build-overviews` 建一次（实测 174 秒），之后 z=13 → **700 ms（149×）**。

⚠️ **代价（必须提前告知用户）**：对本 BigTIFF，GDAL 把概览**写进文件内部**，
不是 `.ovr` 边车 —— 源影像 **3.48 GB → 4.66 GB（+1.19 GB）**，且本机 `rio` 无法清理。

✅ **已改为安全模式（2026-10-17）**：`tile_server.py` 现在有 `--ovr-mode`，**默认 `auto`
永不修改源文件**：

| mode | 行为 | 改源文件？ |
|---|---|---|
| `auto`（默认） | 有 `gdaladdo` → `-ro` 生成外置 `.ovr`；否则**复制副本**建内部金字塔 | **否** |
| `copy` | 总是复制副本 | 否 |
| `gdal` | 强制外置 `.ovr`（无 gdaladdo 则报错） | 否 |
| `inplace` | 就地写入（旧行为，需显式指定） | **是** |

> ⚠️ 常见误解：**"以只读模式打开再 build_overviews 就会自动生成外置 `.ovr`"在 rasterio 里不成立**。
> 实测 `rasterio.open(path, 'r')` 的 `DatasetReader` **根本没有 `build_overviews` 方法**
> （`AttributeError`）；`'r+'` 则写进文件内部。`rio overview` 也没有只读选项。
> 只有 GDAL CLI 的 `gdaladdo -ro` 才支持"只读建外置概览"。

### 坑 4 · 组件抛错会卸载整棵 React 树（整页白屏）

```text
Uncaught Error: Style is not done loading.
The above error occurred in the <MapCanvas> component:
Consider adding an error boundary to your tree to customize error handling behavior.
```

Terra Draw 的 MapLibre adapter 在 `start()` 时会向地图注册自己的 source / layer；
若此时 map style 还没加载完，会抛 `Style is not done loading.`。
而它发生在 React 的 effect 里 —— **React 18 未捕获时会卸载整棵树**，用户看到整页空白。

**两处修法（缺一不可）**：
1. Terra Draw 的创建 + `start()` **必须放进 `map.on('load')` 回调内**；
2. 给每个区域包 **ErrorBoundary**（地图挂了，工具栏 / 图层面板 / 状态栏仍可用）。

> 这个坑的表现是"整个界面消失"，非常容易被误判成"环境问题"而查错方向。

### 坑 5 · 网格索引 `i` 的范围必须逐 `j` 计算

格点沿行方向的投影是 `alongU = i*pitch + j*skew`，反解 `i = (du - j*skew)/pitch`。
`j*skew` 在离原点较远的要素上可达 **±50 个格位**。若用"全局 `iMin`/`iMax`"一次算死，
**远处的要素一个格点都取不到** —— 实测症状是 5,771 m² 的连片空地排坑得 0 株、
全园只有 286 株（正确值 2,152）。

### 坑 6 · 经纬度→米不能用「1° ≈ 111320 m」常数

在纬度 1.18° 处，子午圈每度只有 **110,577 m**。用常数会让面积系统性偏大 **+0.67%**
（实测 TS 合计比 Python/UTM 大 0.75%）。
**修法**：用大地测量曲率半径（M 子午圈 / N 卯酉圈），修正后误差降到 **0.09%**。

### 坑 7 · 估算必须按类别分口径

`vacant_slot`（株位空缺）是"一个种植单元里少了 1 棵树"（实测 253 块 / 16,043 m² ≈ 63 m²/块，
接近一个单元 60.37 m²）。两个坑：
① 网格法用 2 m 退让去铺 8.45 m 间距的格点会大量落空；
② 面积法 `floor(63/66.67) = 0`。
→ **两个口径都必须记 1 株**，点位取质心。

### 坑 8 · MapLibre `match` 表达式的 TS 类型

表达式是变长元组，TS 无法从 `flatMap` 推断形状。
**修法**：收敛到 `lib/classes.ts` 的 `classColorExpr()` 一处做断言，别散落在组件里。

1.0 m → 3,091；2.0 m → 2,184。

> ⚠️ **务必用 `wgr17-final-gaps.geojson`**。`wgr17-elev-gaps.geojson` 是**未应用森林掩膜的
> 中间版**（open_patch 464 / vacant_slot 256，比交付版多 18 块），在它上面跑得
> **3,912 点** —— 数字更大但口径错误。CLI `--input` 默认已改为 final。

1. **HTTP 端点**：`GET /planting-points?clearance=0.5` 返回点位 GeoJSON（含 `meta.total`
   与 `by_class`）。**前端不要自己算放样点** —— 那是局部等距圆柱近似，1.0/2.0 m 档差 0.6~0.9%。
   前端自算只用于拖动时的即时反馈。

2. **前后端株数已对齐（不再是 +8.8%）**：`/gaps` 响应会动态补
   `planting_grid.anchor_lon/anchor_lat`（结果中心最近的格点，**不改磁盘文件**），
   前端用它当网格原点后：0.5 m 档 **3,691 = 3,691（0.00%）**，1.0 m +0.61%，2.0 m +0.92%。
   残余差异来自 GEOS `buffer(-d)` 与逐点距离的数值精度。**对外报数以 Python 为准。**

3. **"树心到最近格点 P50 = 3.15 m" 不是缺陷**（这条之前被误读成"比随机还差"）：
   单株 Voronoi 面积 `A = 8.45 × 7.3179 = 61.836 m²`，二维随机
   `r₅₀ = √(A/2π) = 3.137 m`（实测 3.15）、`P(≤1m) = π/A = 5.08%`（实测 5.1%）——
   **实测就是完美随机**。局域相位重拟合只到 7.3%，**已决定不做**（严守 Stage 14 冻结）。
   业务含义：`open_patch` 按标准株行距铺点供挖坑（间距对即可，**不要宣称"复现原株位"**）；
   `vacant_slot` 用质心，不受影响。

## 17. 多进程跑批（`--workers`，2026-10-17 已实现）

**用法**

```bash
# CLI
python scripts/process_image.py --input ... --workers 4

# sidecar（契约参数，默认 1；0=自动 min(6, cpu//2)）
{"cmd":"detect","params":{"input":"...","workers":4}}
```

**实测（本机 8 核）**

| 场景 | workers | 耗时 | 加速 |
|---|---|---|---|
| ROI 121 瓦片 | 1 | 462 s | 1.00× |
| ROI 121 瓦片 | 4 | **195 s** | **2.37×** |
| 全量 528 瓦片 | 1（历史基线） | 1,048 s | 1.00× |
| 全量 528 瓦片 | 6 | **350 s** | **3.00×** |

ROI 那组的 639 个要素与 13 个 summary 字段**逐位完全相等**。

**四条护栏（实现要点）**

1. **按 `tile_idx` 排序后再累加** —— worker 返回 `(idx, ...)`，主进程
   `results.sort(key=idx)` 后才累加 `all_features` / `class_totals` / `area_total`。
   不排序会让浮点加法顺序变化 → 末位抖动 → 破坏逐位可复现。
2. **`ProcessPoolExecutor(initializer=...)` 只开一次句柄** —— Windows 是 spawn，
   `DatasetReader` 不可 pickle；否则 528 瓦片要开 1,500+ 次大文件。
3. **initializer 里锁线程** —— `OMP/MKL/OPENBLAS/NUMEXPR/GDAL_NUM_THREADS=1`，
   否则多进程 × 多线程会互相抢 CPU，比单进程还慢。
4. **子进程不写 stdout** —— sidecar 的 stdout 是 NDJSON 通道，进度全部由主进程输出；
   两处 `main()` 都加了 `mp.freeze_support()` 为打包做准备。

**两个刻意的设计**

- `workers` **不进参数指纹**：进程数不影响单瓦片结果，改它不该让 528 瓦片缓存失效。
- 瓦片数 < `max(4, workers*2)` 时**自动退回串行** —— Windows 每子进程启动约 1 秒，
  小批量起池反而慢；这也让契约测试（合成小影像）保持确定性。

> ⚠️ 与 10-16 历史结果对比时注意：中间影像建过金字塔（3.48 → 4.66 GB），
> overview 降采样方式改变会让有效性排序变化 → 网格 8.45/7.32 → 8.35/7.23。
> 这是**影像文件层面**的变化，不是 workers 引入的。

## 18. Tauri ↔ sidecar IPC 桥接 与 编辑合并策略（2026-10-17 已实现）

### 18.1 IPC 桥接（`src-tauri/src/lib.rs`）

**命令**：`run_detect` / `cancel_detect` / `detect_status`

```
前端 invoke('run_detect', { params })
  → Rust spawn python sidecar.py --params-json <json>
     ├─ 线程 A：stdout → 逐行 JSON → emit('sidecar-event')
     └─ 线程 B：stderr → emit('sidecar-log')
  → 前端收到 event=result → fetch('/gaps') → 合并人工编辑
```

**五条护栏**

| # | 约束 | 不做的后果 |
|---|---|---|
| 1 | **两个线程分别读 stdout 与 stderr** | Windows 64 KB 管道填满 → sidecar 永久死锁（无报错） |
| 2 | 注入 `PYTHONUNBUFFERED=1` / `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1` | 中文乱码 / UnicodeEncodeError；progress 攒满 8 KB 才吐 |
| 3 | `CREATE_NO_WINDOW` | 每次点检测闪一个黑框 |
| 4 | 前端 `isTauri()` 判断 + 动态 `import('@tauri-apps/api')` | Headless Chrome 里 `invoke` 抛错 → React 卸载整棵树 → 白屏 |

## 19. 打包分发（PyInstaller 单入口 + Tauri resources，2026-10-17 已实现）

### 19.1 单入口（`scripts/desktop_entry.py`）

桌面端要拉起两个 Python 进程：`tile_server`（常驻）与 `sidecar`（按需）。
各打一个 `--onedir` 会把 rasterio/numpy/scipy/shapely/pyproj 的动态库复制两遍
（~350 MB → ~700 MB）。所以做**一个**入口，靠第一个参数分发：

```
desktop_entry.exe --run-tile-server [...]   # 转发给 tile_server
desktop_entry.exe [sidecar 参数...]         # 默认走 sidecar
desktop_entry.exe --self-test               # 冻结态自检（单行 JSON）
```

打包结果：`desktop/runtime/desktop_entry/` = **179 MB**（含 Python 3.11 运行时）。

### 19.2 四条打包红线

| # | 约束 | 不做的后果 |
|---|---|---|
| 1 | `multiprocessing.freeze_support()` 是 `__main__` **第一行** | 进程池子进程带 `--multiprocessing-fork` 重新执行 exe，被 argparse 拦掉 → `--workers > 1` 崩 |
| 2 | `--collect-all rasterio / pyproj / shapely` | Cython `.pyd` 与 `proj.db`/`gdal_data` 抓不全 → 运行期 `ModuleNotFoundError` / `Cannot find proj.db` |
| 3 | 冻结态自定位 `PROJ_DATA` / `GDAL_DATA` | 这两个库只认环境变量，冻结后不知道数据在哪 |
| 4 | 打包态工作目录必须**可写** | 装到 `Program Files` 时安装目录只读，写 `output/` 与瓦片缓存失败 |

### 19.3 ⚠️ 实测抓到的坑：两份 `proj.db` 版本不同

```
CRSError: The EPSG code is unknown. PROJ: proj_create_from_database:
... proj.db contains DATABASE.LAYOUT.VERSION.MINOR = 4
whereas a number >= 5 is expected. It comes from another PROJ installation.
```

- `rasterio 1.4.4`（GDAL 3.10.3）自带 `rasterio/proj_data/proj.db` → **MINOR=5**
- `pyproj 3.7.2` 的 pip 包自带 `pyproj/proj_dir/share/proj/proj.db` → **MINOR=4**（旧）

把 `PROJ_DATA` 指向 pyproj 那份时，rasterio 的 GDAL 直接拒绝加载 →
所有 `CRS.from_epsg(...)` 失败、瓦片服务全崩。

**修法**：`PROJ_DATA` 优先指向 **rasterio 的 `proj_data`**（更新），pyproj 兜底
（PROJ 向前兼容，pyproj 读新库没问题）。

> 这个坑**只在冻结态出现** —— 开发态两个库各自找自己的数据，互不干扰。
> 所以 `--self-test` 里专门加了 `gdal_driver_ok`（用 MemoryFile 真开一个 GTiff），
> 否则要等到用户点开地图才发现。

### 19.3b 产物位置：固定在项目内（2026-10-17 用户要求）

与其他项目保持一致：编译产物与安装包都在**项目文件夹内**


若不处理，cargo 会把产物甩到那里（项目外），卸载 / 清理 / 交付都很别扭。

## 22. 复核效率三件套（P1，2026-10-18 已实现）

### 22.1 为什么先做这个

1,726 个多边形里有 465 块 `uncertain`（待复核，40,593 m²）。原来的界面里

### 22.2 撤销/重做

| 项 | 决定 | 理由 |
|---|---|---|
| 存储 | 快照 `gaps.slice()` | 要素对象不可变 → 结构共享，约 14 KB/步 |
| 上限 | 40 步 | 40 × 14 KB < 1 MB，够用且不会失控 |
| 批量 | **一次操作 = 一步** | 否则框选 40 块删除要按 40 次 Ctrl+Z |
| 新操作 | 清空重做栈 | 否则时间线分叉 |
| 拖拽 | 1.5 s 时间窗合并 | TerraDraw 每次移动都发 change，不合并会吃光栈 |
| 换基线 | `setGaps` 清空历史 | 撤销到"上一份数据"没有意义 |

### 22.3 框选

判定抽成 `lib/selection.ts` 的纯函数，**强制传 `visibleClasses`**：
默认只勾选「确定需补种」，隐藏的道路/水体若被框选中，一次批量删除就会
静默抹掉 180 条道路而地图上看不出来。

不用 `queryRenderedFeatures`：结果随缩放级别变化、跑在 WebGL 里测不到、
且不区分类别可见性。

交互侧：进模式时 disable `dragPan` / `boxZoom`（MapLibre 默认把 Shift+拖拽
绑成拉框放大）；`mouseup` 挂 window，拖到画布外也能收尾。
