# 推理服务契约（Python sidecar）

> **状态**：v1 草案 · 2026-10-13
> **适用范围**：`scripts/sidecar.py` ↔ Tauri/Rust 宿主进程之间的进程边界
> **上游依据**：`scripts/process_image.py`（v0.3，已验证跑通整幅 321 瓦片）

---

## 0. 这份文档解决什么问题

Python 侧的算法链路**已经能跑通**（`process_image.py` 实测整幅 229 公顷、321 个有效瓦片、1172 秒）。但它现在是个**给人用的命令行工具**：

- 参数靠 `argparse` 传，几十个开关
- 进度是 `print()` 出来的中文日志，格式自由
- 结果写成一个 GeoJSON 文件

Tauri 那边要调它，**不能靠解析人类的日志**。这份契约把"人机接口"改造成**机器接口**：

| | 现在（人用） | 契约后（机器用） |
|---|---|---|
| 传参 | `--input xx.tif --exg-lo 40` 一串开关 | 一个 JSON 对象 |
| 进度 | `[13:24:01] 进度 15/321（4.7%）用时 120s` | `{"event":"progress","done":15,"total":321,...}` |
| 结果 | 写文件，人去打开 | 事件流里直接给出路径 + 摘要 |
| 报错 | 返回 1，日志里找原因 | `{"event":"error","code":"E1001",...}` |

**设计原则**：`sidecar.py` **不重写任何算法**。它只做三件事——把 JSON 参数翻译成 `process_image` 的入参、把内部进度转成结构化事件、把结果包成机器可读的响应。算法仍然只有一份，在 `process_image.py` / `grid_prior.py` / `detect.py` 里。

**为什么这样做**：两边可以并行开发。Tauri 那边照契约先用手写的假事件流调通界面，Python 这边慢慢优化算法，互不阻塞。

## 1. 进程模型

```
┌──────────────────────────────────────────┐
│  Tauri 宿主（Rust）                        │
│                                            │
│  1. 拼一个 JSON 参数对象                    │
│  2. spawn 子进程：                          │
│     python sidecar.py --params-json '{...}'│
│                                            │
│  3. 按行读 stdout（NDJSON 事件流）          │
│     ┌────────────────────────────────┐    │
│     │ {"event":"started",...}         │    │
│     │ {"event":"progress",...}        │    │
│     │ {"event":"result",...}          │    │
│     └────────────────────────────────┘    │
│                                            │
│  4. 退出码 0 = 成功，非 0 = 失败            │
└──────────────────────────────────────────┘
              │ spawn
              ▼
┌──────────────────────────────────────────┐
│  Python sidecar                            │
│  - stdin : 参数 JSON（或 --params-json）    │
│  - stdout: **只输出 NDJSON 事件**，一行一个 │
│  - stderr: 人类诊断日志（可丢弃、可显示）   │
└──────────────────────────────────────────┘
```

**关键约定**：

1. **stdout 是数据通道，只允许出现 NDJSON**。任何调试输出必须走 stderr，否则会污染事件流。
2. **一行一个 JSON 对象**（NDJSON / JSON Lines），不跨行、不带逗号结尾。宿主按 `\n` 切分逐行解析。
3. **UTF-8 编码**，`ensure_ascii=False`（中文直接输出，不转义成 `\uXXXX`）。
4. **每行写完立即 flush**，宿主才能实时收到进度（Python 的 `print(flush=True)` 或 `sys.stdout.flush()`）。
5. **终止信号**：宿主关闭 stdin 或发 SIGTERM 时，sidecar 应尽快退出。Windows 下用 `CTRL_BREAK_EVENT` 或直接 kill。

## 2. 入参（请求）

### 2.1 传递方式

二选一，按宿主方便程度：

```bash
# 方式 A：命令行内联（参数短时方便）
python scripts/sidecar.py --params-json '{"input":"D:/WGR/WGR17.tif","job":"wgr17-full"}'

# 方式 B：stdin（参数长时避免命令行长度限制）
echo '{"input":"..."}' | python scripts/sidecar.py --params-stdin

# 方式 C：参数文件（便于留档、复现）
python scripts/sidecar.py --params-file job.json
```

### 2.2 参数对象 Schema

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|

| `job` | string | | `"wgr17-full"` | 任务名，决定中间态目录名 `output/jobs/<job>/` |

| `tile_size` | int | | `2048` | 瓦片边长（像素） |
| `overlap` | int | | `128` | 瓦片外扩（像素），≈4.2 m |
| `limit` | int \| null | | `null` | 只处理前 N 个瓦片（试跑用） |
| `force` | bool | | `false` | 忽略瓦片缓存，全部重算 |

| `exg_threshold` | float \| null | `null` | 非 null 时改用固定绝对阈值；负数视为回退到混合判据 |

| `min_gap_blob` | int | `200` | 空地最小斑块（像素），去噪 |
| `min_gap_width_m` | float | `1.6` | 空地分离开运算半径依据（米） |
| `separate_gaps` | bool | `true` | 是否做空地分离 |
| `min_area` | float | `30.0` | 最小空地面积（m²） |
| `simplify_m` | float | `0.3` | 多边形简化容差（米，Douglas-Peucker） |

**网格先验参数**：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `prior_pitch_m` | float | 见代码 | 株距先验（米） |
| `node_tol_ratio` | float | `0.35` | 株位容差比例 |
| `elongate_ratio` | float | `2.2` | 长宽比阈值（区分连片空地/林间空隙） |
| `min_coverage_for_slot` | float | `0.15` | 判定"株位空缺"的最小覆盖率 |
| `survey_samples` | int | `7` | 网格勘察采样数 |
| `target_density_per_ha` | float | `150.0` | **园区设计密度**（株/公顷）。油棕园常规设计至多 150 株/ha。用于**交叉校验**网格估计结果 —— 估计密度若偏离设计值超过 ±10% 会告警。桌面端（Tauri）应允许用户配置。传 `0` 表示不校验 |

**不可种植地物参数**（2026-10-13 新增，用户要求把道路/水体/办公区从补种面积中扣除）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `landcover_unplantable` | bool | `true` | 是否检测道路/水体/办公区。`false` 时退化为旧行为 |
| `unplantable_overlap` | float | `0.5` | **已失效**，仅为向后兼容保留（现改为按像素几何差集扣除，不再用整块改判阈值） |

**草地回检参数**（2026-10-13 新增，修正"草地被误判成油棕导致漏检"）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `grass_recheck` | bool | `true` | 是否做草地回检：把"过于鲜绿且连片"的区域从树冠中剔除 |
| `grass_grid` | bool | `true` | 草地回检的第二道判据（株行距网格周期性回检，方案 B）：树心按 8.45 m 规则排列的候选区判为油棕林并剔除，只保留无空间周期的真草地 |

**其他**：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `quiet` | bool | `false` | 精简 stderr 日志（不影响 stdout 事件） |
| `progress_every` | int | `20` | 每处理多少个瓦片发一次 progress 事件（宿主可调） |

**校验规则**（契约的一部分，宿主可提前自查）：

- `input` 必须存在且可读 → 否则 `E1001`
- `tile_size` 必须 ≥ 256 且是 2 的幂 → 否则 `E1002`
- `overlap` 必须 ≥ 0 且 < `tile_size/2` → 否则 `E1002`
- `pct` 必须在 (0, 100] → 否则 `E1002`
- `exg_lo` < `exg_hi` → 否则 `E1002`
- `method` 只接受白名单值 → 否则 `E1002`
- 未知字段：**忽略但告警**（向前兼容，宿主升级不影响旧 sidecar）

## 3. 出参（事件流）

### 3.1 事件通用结构

每个事件都是一个 JSON 对象，必带 `event` 字段表明类型：

```json
{"event": "<类型>", ...类型专属字段}
```

事件类型共 6 种：

| `event` | 何时发 | 宿主应做什么 |
|---|---|---|
| `started` | 进程启动、参数校验通过后 | 记录日志；可展示"已开始" |
| `log` | 关键阶段里程碑 | 显示进度文字（如"网格勘察完成"） |
| `progress` | 每 N 个瓦片 / 阶段推进 | 更新进度条 |
| `result` | 全部成功、结果已落盘 | 读取 `out_json`，进入渲染 |
| `error` | 发生错误（终态） | 按 `code` 分类处理，展示 `message` |
| `warn` | 非致命告警 | 提示用户但不中断 |

**终止条件**：

- 收到 `result` → 成功，进程随后以退出码 0 结束
- 收到 `error` → 失败，进程随后以退出码 ≠ 0 结束
- 两者**必有其一**且**只出现一次**（保证宿主能确定终态）

### 3.2 `started` 事件

```json
{
  "event": "started",
  "job": "wgr17-full",
  "pid": 12345,
  "sidecar_version": "1.0.0",
  "schema_version": "0.3",
  "params_echo": { "...归一化后的参数..." },
  "started_at": "2026-10-13T05:24:01.123456+00:00"
}
```

说明：`params_echo` 是**归一化后的实际生效参数**（补全默认值、解 bool 开关），宿主可直接固化到结果档案里做复现依据。

### 3.3 `log` 事件（里程碑）

```json
{
  "event": "log",
  "level": "info",
  "stage": "grid_survey",
  "message": "网格勘察完成：株距 8.35 m，行距 7.23 m，错行角 60.0°，质量 0.734"
}
```

`stage` 枚举（宿主可据此在界面上打勾）：

| `stage` | 含义 |
|---|---|
| `open_image` | 打开影像、读取元数据 |
| `plan_tiles` | 瓦片规划完成 |
| `grid_survey` | 全局网格勘察完成 |
| `tile_processing` | 逐瓦片推理阶段 |
| `merge` | 合并整幅结果 |
| `export` | 结果落盘 |

### 3.4 `progress` 事件

```json
{
  "event": "progress",
  "stage": "tile_processing",
  "done": 15,
  "total": 321,
  "ratio": 0.0467,
  "elapsed_s": 120.4,
  "eta_s": 2334.0,
  "tiles_new": 15,
  "tiles_cached": 0,
  "tiles_failed": 0,
  "gaps_found": 42,
  "gap_area_sqm": 11234.5,
  "message": "进度 15/321（4.7%）"
}
```

字段说明：

- `ratio` = `done / total`，宿主直接用，不用自己算
- `eta_s`：预计剩余秒数；无法估算时为 `null`
- `gaps_found` / `gap_area_sqm`：**累计值**，便于界面实时显示"已发现 X 块空地 / Y 平方米"
- `tiles_cached`：命中缓存的瓦片数（断点续跑时不为 0）

**频率**：默认每 `max(1, total // 20)` 个瓦片发一次（即约 20 次进度更新），可由 `progress_every` 覆盖。**首尾必发**——第 1 个瓦片处理完发一次，最后一个瓦片处理完必发一次（`done == total`）。

### 3.5 `warn` 事件

```json
{
  "event": "warn",
  "code": "W2001",
  "message": "全局网格质量 0.112 < 0.15，本次所有空地都会被标为「不确定」并交人工复核"
}
```

常见告警（详见 §5 告警码）：

- 网格质量过低（影像可能不是规整种植园）
- `kml` 参数被传入但本版未启用
- 参数对象中存在未知字段
- 部分瓦片处理失败（不致命，最终结果仍产出）

### 3.7 `error` 事件

```json
{
  "event": "error",
  "code": "E1001",
  "message": "找不到影像文件 D:/WGR/WGR17.tif",
  "detail": "FileNotFoundError: [Errno 2] No such file or directory: 'D:/WGR/WGR17.tif'",
  "stage": "open_image",
  "recoverable": false,
  "finished_at": "2026-10-13T05:24:02.123456+00:00"
}
```

- `message`：面向用户的中文说明，**可直接显示在界面上**
- `detail`：原始异常信息（`类型: 消息`），面向开发者，用于排查；可能较长（截断至 300 字符）
- `stage`：出错时所在阶段，同 §3.3 的枚举
- `recoverable`：`true` 表示换个参数/修一下还能重跑；`false` 表示需要人工介入

## 4. 退出码

| 退出码 | 含义 | 伴随事件 |
|---|---|---|
| `0` | 成功 | `result` |
| `1` | 用户级错误（参数非法、文件缺失、CRS 不兼容等） | `error`，`recoverable` 多为 `true` |
| `2` | 内部错误（未捕获异常、依赖缺失、内存不足） | `error`，`recoverable` 为 `false` |
| `3` | 被宿主中断（收到终止信号） | 无终态事件 |
| `130` | 被 SIGINT（Ctrl+C）中断 | 无终态事件 |

**注意**：即使收到 `error` 事件、进程即将以非 0 退出，**sidecar 也应把该事件完整写到 stdout 并 flush 后再退出**，避免宿主因事件丢失而拿不到失败原因。

## 5. 错误码与告警码

沿用项目既有分段约定（`E1xxx` IO / `E2xxx` CRS / `E3xxx` 推理 / `E4xxx` 矢量化 / `E5xxx` 导出 / `E9xxx` 内部）。

### 5.1 错误码（`error` 事件的 `code`）

| 码 | 触发条件 | 建议宿主提示 |
|---|---|---|
| `E1001` | 输入影像不存在 / 不可读 | 「找不到影像文件，请确认路径」 |
| `E1002` | 参数非法（超出范围、枚举值错误、类型不符） | 「参数 X 的取值不合法」 |
| `E1003` | 输出路径不可写（磁盘满 / 无权限） | 「无法写入结果文件」 |
| `E1004` | 影像格式不受支持（非 tif/GeoTIFF） | 「不支持该影像格式」 |
| `E1005` | 影像缺少地理坐标信息（无 CRS/transform） | 「影像没有坐标信息，无法计算实际面积」 |
| `E2001` | CRS 无法识别 | 「无法识别影像坐标系」 |
| `E2002` | 重投影失败（目标 EPSG:32649） | 「坐标转换失败」 |
| `E2003` | 影像不在预期经纬度范围内（可能拿错文件） | 「影像位置异常，请确认是否为目标园区」 |
| `E3001` | 推理阶段全部瓦片失败（无任何有效结果） | 「检测未能获得有效结果」 |
| `E3002` | 网格勘察失败（无足够采样点） | 「无法识别种植网格，请确认影像为油棕园区」 |
| `E4001` | 栅格转矢量失败 | 「空地轮廓提取失败」 |
| `E4002` | 多边形简化失败 | 「结果后处理失败」 |
| `E5001` | GeoJSON 写出失败 | 「结果导出失败」 |
| `E9001` | 未捕获的内部异常 | 「内部错误，请把日志反馈给开发者」 |
| `E9002` | Python 依赖缺失（rasterio / shapely 等） | 「运行环境不完整，请先执行环境配置」 |

### 5.2 告警码（`warn` 事件的 `code`）

告警**不中断**流程，只提示：

| 码 | 触发条件 |
|---|---|
| `W1001` | 参数对象含未知字段（已忽略） |
| `W1002` | `kml` 参数已传入但本版未启用（已忽略） |
| `W2001` | 全局网格质量 < 0.15（结果整体不可信） |
| `W3001` | 网格质量 < 0.4（结果需人工抽查） |
| `W3002` | 部分瓦片处理失败（已跳过，结果仍产出） |
| `W3003` | 有效数据占比 < 30%（影像大部分是 NoData） |
| `W4001` | 空地总面积占比 > 25%（可能是判据过松，建议复核） |

> `W4001` 的现实意义：本轮实测空地占 12.46%，若某次跑出 >25%，多半是 `--exg-lo` 标定不对导致树冠被误判成空地——**这正是需要一个告警来提醒的典型场景**。

## 6. 结果文件（`out_json`）

`out_json` 指向的文件即 `process_image.py` 现在产出的整幅 GeoJSON，**格式不变**（`schema_version = "0.3"`）。本契约不重新定义它，只在这里给出索引，避免两处维护：

- **顶层字段**：`type` / `schema_version` / `crs` / `area_crs` / `source_image` / `kml_source` / `used_kml` / `generated_at` / `processing` / `planting_grid` / `grid_survey` / `params` / `model` / `blocks` / `summary`
- **几何数据在** `blocks[].gaps[]`（**注意：顶层 `features` 恒为空数组**，这是为了 GeoJSON 兼容性保留的占位）
- **汇总指标在** `summary`

完整字段说明见：
- `docs/01-需求与架构/需求文档.md` §A.5（注意该节写的是 v0.2 单类版，**实际代码已是 v0.3 四类版**，差异见下）
- 实际样例：`output/wgr17-full-gaps.geojson`

**与需求文档 §A.5 的已知差异**（以代码为准）：

| 项目 | 需求文档 §A.5 | 实际代码 v0.3 |
|---|---|---|
| `schema_version` | `"0.2"` | `"0.3"` |
| `class` 取值 | 固定 `"vacant"` | `vacant_slot` / `alley_gap` / `open_patch` / `uncertain` |
| `class_method` | `"single_class"` | `"planting_grid_prior"` |
| `area_crs` | 无此字段 | `"EPSG:32649"`（面积在 UTM 下算） |
| 顶层 `features` | 无 | 恒为空数组占位 |

> **待办**：需求文档 §A.5 需同步到 v0.3，否则新人读了会以为 `class` 只有一种取值。

## 7. 中间态与断点续跑

契约要求 sidecar **保留** `process_image.py` 的断点续跑能力，宿主可借此实现"暂停/恢复"：

```
output/jobs/<job>/
├── grid-survey.json          ← 网格勘察结果（含参数指纹）
└── tiles/
    ├── r000000_c002048.json  ← 单瓦片结果（含参数指纹）
    └── ...
```

**参数指纹**：由「影像 size/mtime」+「关键参数 SHA256 前 16 位」合成。宿主行为建议：

- 指纹一致 → 瓦片缓存有效，重跑会**秒级完成**（全部命中缓存）
- 指纹不一致 → 缓存自动失效，**全部重算**
- 想强制重算 → 传 `force: true`

**宿主可用的续跑策略**：

1. 用户改了 `exg_lo` 之类的参数 → 指纹变化 → 自动全量重算（正确行为，无需宿主干预）
2. 上次跑到一半崩了 → 直接重跑同一 `job`，已完成的瓦片会命中缓存，只补算剩下的
3. 只想看汇总不想重算 → 传 `merge_only: true`

## 8. 兼容性与版本

- `sidecar_version`：sidecar 自身的版本号（语义化版本），出现在 `started` 事件
- `schema_version`：**结果 JSON 的 schema 版本**，当前 `"0.3"`，同步出现在 `started` 与结果文件里
- **宿主必须容忍未知事件类型和新字段**（向前兼容），遇到不认识的事件忽略而非报错
- **`schema_version` 主版本变更**（如 0.3 → 1.0）属破坏性变更，需两边同步升级；次版本变更（0.3 → 0.4）为兼容性增强

## 9. 最小可用示例

### 9.1 宿主侧伪代码（Rust，示意）

```rust
let params = serde_json::json!({
    "input": "D:/WGR/WGR17.tif",
    "job": "wgr17-full",
    "progress_every": 10
});

let mut child = Command::new("python")
    .args(["scripts/sidecar.py", "--params-stdin"])
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .spawn()?;

// 写参数并关闭 stdin
child.stdin.take().unwrap()
     .write_all(params.to_string().as_bytes())?;

// 按行读事件
let reader = BufReader::new(child.stdout.take().unwrap());
for line in reader.lines() {
    let ev: serde_json::Value = serde_json::from_str(&line?)?;
    match ev["event"].as_str() {
        Some("progress") => update_progress_bar(&ev),
        Some("result")   => load_geojson(ev["out_json"].as_str().unwrap()),
        Some("error")    => show_error(&ev),
        _ => {}   // 未知事件忽略（向前兼容）
    }
}
```

## 11. 未决问题

以下问题需要与宿主侧确认后才能冻结契约（当前给了**默认取值**，先按默认跑）：

| # | 问题 | 当前默认 |
|---|---|---|
| Q1 | 宿主需要"预估总耗时"吗？现有 ETA 基于已处理瓦片速率推算，**冷启动阶段（前 20 个瓦片）很不准** | 提供 `eta_s`，但声明冷启动不可信 |
| Q2 | 需要"分块结果"事件吗？即每个瓦片算完立刻推它的空隙几何，让界面边算边画 | **不提供**，只在 `result` 里给整幅。理由：跨瓦片质心归属要去重，边算边画会出现重复/丢块 |
| Q3 | 中断后能否恢复？现有断点续跑是**瓦片级**的，重启同一 `job` 即可 | 宿主用"重跑同 job"实现恢复，无独立 `resume` 命令 |
| Q4 | 是否支持多影像批量？ | **暂不支持**，一次一个影像。批量由宿主循环调用 |
| Q5 | Python 解释器路径谁负责？ | 由宿主配置（项目 `.venv` 或打包的 embedded python），sidecar 不假设 |
