# 桌面端交互需求与实现映射（v0.4）

> 起因：2026-10-17 用户提出 5 步桌面端工作流需求（导入渲染 → 圈选 Target Block →
> 分类渲染与过滤 → 增删多边形 → 推理估算 + 导出），并转来一份外部 AI 的技术方案。
> 本文做两件事：① **裁定技术栈冲突**（外部方案 vs 项目已冻结架构）；
> ② **把 5 项需求逐条映射到现有代码能力**，标出哪些已具备、哪些要新做。

**外部方案里真正有价值、且项目尚未覆盖的两条**（已采纳进第 2 节）：
1. **ROI 圈选能同时解决"边界外误判"与"跑批太慢"** —— 与项目已规划但未实现的 KML 裁剪能力直接对应；
2. **按株行距网格"排坑模拟"生成补种点位** —— 正是 PRD 里挂了很久的 Q5「补种点位置尚未生成」。

### 0.2 为什么不改成 FastAPI HTTP 微服务

外部方案建议"Python 常驻 `127.0.0.1:8765` 提供 REST"，但项目**已经有一套更严格的进程边界**：

| 维度 | stdio NDJSON sidecar（现行） | FastAPI HTTP 微服务 |
|---|---|---|
| 端口占用 | 无（进程管道） | 需占用端口，可能被防火墙/杀软拦、被其它程序抢占 |
| 生命周期 | 随宿主进程生灭，天然无残留 | 需自己管启停、防僵尸进程、防端口冲突 |
| 契约成熟度 | **已冻结并实现**（`推理服务契约.md`，契约测试 95/95） | 需重新设计、重新实现、重新写测试 |
| 进度事件 | 天然流式（stdout 逐行 NDJSON） | 需 SSE / WebSocket 额外机制 |
| 断点续跑 | 已实现（参数指纹 + 瓦片缓存） | 需重新包装 |
| 安全面 | 仅本机进程管道 | 暴露本地 HTTP 端口（其它本机程序可访问） |

**裁定**：算法主链路继续走 stdio sidecar。**唯一例外是瓦片**——浏览器端的 `<img src>` / MapLibre
需要 HTTP 才能取瓦片，所以瓦片服务必须是 HTTP（见第 4 节）。这不是"改用 FastAPI"，
而是"只给瓦片开一个最小 HTTP 端点"。

### 需求 2 · 圈出 Target Block，只检测圈内 —— ❌ **算法侧尚不存在**

这是本次需求里**唯一需要动算法链路**的一项，必须说清现状：

```text
# scripts/process_image.py 现状（第 1395-1461 行附近）
"kml_source": None,          # ← 硬编码
"used_kml": False,           # ← 硬编码
"block_name": "整幅影像（未提供 KML）",   # ← 永远单 block

# scripts/sidecar.py 现状（第 245 行附近）
if values.get("kml"):
    emit_warning("W1002", "kml 参数已传入但本版未启用（P1 功能），已忽略；")
```

**也就是说：KML / ROI 裁剪在算法侧是"预留字段 + 明确告警忽略"，功能没有实现。**
（`需求文档.md` B.7 也把"KML 支持"列为 P1 待办。）

**好消息：实现成本低，因为已有同构机制可抄。** 管线里已经有一个"按多边形掩膜裁剪有效区"
的成熟实现——`--forest-mask`（非种植区掩膜）：

- 它接受一个 GeoJSON 多边形集合 → 栅格化成 bool 掩膜 → 从 `valid` 里扣掉；
- ROI 要的恰好是它的**对偶**：接受多边形 → 栅格化 → 只保留掩膜内的 `valid`。

所以需求 2 的落地路径是：

| 步骤 | 做法 | 复用 |
|---|---|---|
| ① 前端画多边形 / 导入 `.geojson`/`.kml` | Terra Draw | — |
| ② 传给后端 | sidecar 参数 `roi`（GeoJSON 字符串或路径），替代现有 `kml` 占位 | 现有参数表机制 |
| ③ 瓦片级跳过 | 用 ROI 外接框先滤一遍瓦片清单，**圈外瓦片直接不进处理队列** | 现成的 `order_tiles_by_validity` / 瓦片清单 |
| ④ 像素级裁剪 | ROI 栅格化后与 `valid` 取交集 | `--forest-mask` 同构代码 |
| ⑤ 输出记账 | `used_roi` / `roi_source` 字段写进结果 JSON | 现有 `kml_source` 字段改名 |

> **收益（外部方案说得对，且量级可验证）**：本机全量 528 瓦片 / 1,041.6 秒。
> 若用户只圈选目标区块（例如占外接矩形 30%），瓦片数按面积近似线性下降 →
> **跑批时间可降到 5 分钟量级**；更重要的是**圈外的天然林、邻园、道路在算法启动前就被物理隔离**，
> 从此不必再纠结 `forest-mask` 的阈值（当前掩膜对阈值敏感：原始 <70 → 15.4 ha /
> 影响 16.8%；平滑 σ1.5 <90 → 17.0 ha / 20.3%）。

## 2. 两个需要新做的算法能力（设计草案）

### 2.1 ROI 裁剪（需求 2）

见 §1 需求 2 的五步表。**注意一个边界情况**：ROI 边界会切断瓦片，
被切断处不应产生"假空地"（边界外的 NoData 不能被当成空地）。
做法：ROI 掩膜外一律置为 `valid = False`，与现有 `valid` 逻辑一致即可天然规避。

### 2.2 补种点位生成（需求 5，即外部方案说的"排坑模拟法"）

**为什么这个思路是对的**：项目已经有一个拟合好的种植网格 `GridModel`
（`grid_survey`: 株距 8.45 m / 行距 7.32 m / 错行角 60° / 质量 0.752），
它就是"这园子本该怎么种"的数学模型。**"哪里缺了多少棵"本质就是在网格上数空位**，
而不是拿面积除以单株占地。

**算法草案**：

```text
输入：ROI 内的"确定需补种"多边形（open_patch + vacant_slot + manual_add）
     + 全局 GridModel

1. 枚举格点：以 GridModel 为基准，铺出覆盖 ROI 的格点集（UTM 绝对坐标，
   直接复用 GridModel 的 origin / 轴向 / 株距 / 行距 / skew）
2. 保留落在多边形内的格点（shapely.contains / 用 prepared geometry 加速）
3. 安全退让：剔除距多边形边界 < R 的格点
   （R 默认 2.0 m —— 与"距道路/水沟留退让"的业务习惯一致，可配）
4. 避让既有树：剔除距任一 tree_info 树心 < R2 的格点
   （R2 默认 2.0 m；tree_info.json 有 15,190 个树心，实测可用）
5. 输出 Point 集合，每点带：所属多边形 gap_id、格点索引、UTM 坐标、经纬度
```

**两种口径同时给，不要二选一**（外部方案这点也对）：

| 口径 | 算法 | 用途 |
|---|---|---|
| 面积折算 | `floor(area / 66.67)` | 极速，用于实时响应拖动。**是上界** |
| 网格排坑 | §2.2 的 5 步 | 精确，用于最终交付；**并给出可直接放样的 GPS 点位** |

**必须按类别分口径**（前端原型实测驱动，见 `desktop/README.md` §五）：

| 类别 | 口径 | 理由 |
|---|---|---|
| `vacant_slot`（株位空缺） | 两个口径都记 **1 株**，点位取质心 | 它本身就是"一个种植单元里少了 1 棵树"（实测 253 块 / 16,043 m² ≈ 63 m²/块，接近一个单元 60.37 m²）。用 2 m 退让去铺 8.45 m 间距的格点会大量落空；面积法 `floor(63/66.67)` 又会算成 0 |
| `open_patch` / `manual_add` | 网格排坑（含退让） | 多株区域，几何形状决定能放几株 |

**实测结果（1,726 个要素，真实结果）**：

| 项 | 数值 |
|---|---|
| 面积折算 | 4,420 株 |
| 网格排坑（退让 2 m） | **2,152 株** |
| 差异 | **51.3%** |
| 449 块 `open_patch` 中排坑为 0 的 | **123 块 / 31,155 m²**（窄条，2 m 退让后放不下格点） |

**退让距离敏感度**（这是必须由业务拍板的参数）：

| 退让 | 排坑口径 | 与面积口径差异 |
|---|---|---|
| 0.5 m | 3,594 株 | 18.7% |
| 1.0 m | 3,009 株 | 31.9% |
| **2.0 m** | **2,152 株** | **51.3%** |
| 3.0 m | 1,569 株 | 64.5% |

> ⚠️ **必须交叉验证**：两种口径的差值本身就是质量指标。
> 差值大说明该多边形形状破碎、或退让吃掉了大量面积，应当在 UI 上标黄提示复核。
> **结论**：面积口径（`309,143 m² → 约 4,637 株`）是**上界**，几何口径才是可放样的真实数量。
> 差异集中在窄条 —— 这同时提示 `open_patch` / `alley_gap` 的分类边界值得复核
> （2.2 m 宽的行间缝隙本来就不该算作"可补种的连片空地"）。

## 3. 接口蓝图（按项目已有契约改写，**不是** 4 个 HTTP 接口）

外部方案给的是 `POST /api/...` 四接口。按 §0.2 的裁定，主链路改成 **sidecar 命令**，
只有瓦片是 HTTP：

| 步骤 | 通道 | 接口 | 输入 | 输出 |
|---|---|---|---|---|
| 1 | HTTP（唯一） | `GET /tiles/{z}/{x}/{y}.png` | — | PNG 瓦片 |
| 1 | HTTP | `GET /meta` | — | 影像外接框 / CRS / 分辨率 / 有效区占比 |
| 1 | Tauri Command | `import_image` | tif 路径（+ chm / segment 可选） | 打开栅格、建概览、返回 meta |
| 2+3 | sidecar | `detect`（现有 `run`） | 参数 JSON（新增 `roi`） | NDJSON 事件流 → 结果 GeoJSON |
| 4 | Tauri Command | `list_gaps` / `edit_gap` / `delete_gap` / `add_gap` | — | 前端状态（**不重跑算法**） |
| 5a | sidecar | `estimate`（**新增**） | 编辑后的 gaps GeoJSON + 网格模型 | 株数（双口径）+ 补种点位 |
| 5b | sidecar | `export`（**新增**） | 编辑后的 gaps + 目标目录 | `.shp.zip` / `.geojson` / `.kml` / `.csv` |

**新增的两个 sidecar 命令**（`estimate` / `export`）应保持现有契约风格：
参数表 + 别名 + args 赋值 + 回显 + 指纹**五处同步**（`scripts/sidecar.py` 的既有约定）。

## 4. 需要你拍板的三个问题

### 4.1 瓦片服务用 Rust 还是 Python？

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Rust GDAL `TileService`（axum）** —— 架构文档原定 | 与文档一致；打包后无 Python 依赖；性能最好 | 需写 Rust + GDAL 绑定，开发量大；**与"算法已全在 Python"重复造轮子** |
| **B. Python 标准库 `http.server` + `rasterio`** | **零新依赖**（本机已有 rasterio）；与算法同语言、同 CRS 处理代码；**今天就能跑** | 性能一般（但瓦片是 256×256 小请求，实测足够）；需自己管线程 |
| **C. Python FastAPI + `rio-tiler`** | 代码最省（rio-tiler 专为瓦片设计） | 需装 3 个新依赖；引入一个只在原型期用的框架 |

**我的建议：原型阶段用 B，定稿前评估是否值得为性能换成 A。**
理由：本项目已经**在 Python 里实现了整套地理处理**（窗口化读栅格、CRS 转换、栅格化掩膜、
矢量化），Rust 侧重写这些属于**重复实现已验证代码**，风险高收益低。
真正需要 Rust 的只有：窗口/菜单/文件对话框、进程监督、以及把瓦片端点包成 Tauri 的一部分。

> ⚠️ 这条建议**偏离了 `架构方案.html` 的原文**（原文把地理内核放在 Rust）。
> 但那份文档写于 2026-10-12，当时算法还没落地；现在算法已跑通并逐位可复现，
> 前提变了。**是否改架构请用户明确表态**，我不擅自改权威文档。

### 4.2 地理内核（RasterReader / TileScheduler / Vectorizer）留在 Python 吗？

同上，建议**保留在 Python**。这三个模块在 `process_image.py` 里都已实现并经过
528 瓦片实测，重写为 Rust 等于把"已验证"换成"未验证"。

### 4.3 补种点位的业务规格（**实测已给出敏感度，请选一个**）

退让距离直接决定苗木量，实测敏感度（全园，真实结果）：

| 退让 | 排坑口径 | 说明 |
|---|---|---|
| 0.5 m | 3,594 株 | 相当于"贴着树冠边缘也能种" |
| 1.0 m | 3,009 株 | |
| **2.0 m** | **2,152 株** | 原型默认；≈ 半个冠幅 |
| 3.0 m | 1,569 株 | ≈ 一个冠幅，最保守 |

- 安全退让 R 默认 **2.0 m** 是否合适？（外部方案建议 2 m）
- 是否需要**避让既有树心**（R2 = 2.0 m）？还是允许"补种在现有树旁"？
  → 原型**尚未接入** `tree_info.json`（15,190 个树心）做交叉剔除，
  这是正式版的必要一步
- 输出格式：GeoJSON Point 集合是否够？还是也要一份**可导入手持 GPS 的 CSV/KML**？

| 1 | ROI 裁剪实现后，边界瓦片可能出现"贴边假空地" | 边界处误报 | ROI 掩膜外强制 `valid=False`；交付前目视复核边界 |
| 2 | 补种点位与 `tree_info` 树心口径不一致 | 点位落在已有树上 | 用 tree_info 做交叉剔除；给"距离最近树心"字段供复核 |
| 3 | 前端 1,700+ 多边形在低配机器上渲染卡顿 | 交互体验 | MapLibre 矢量图层 + 按需只渲染当前视口；必要时加 `deck.gl`（架构文档已列为可选） |
| 4 | 人工增删的多边形**没有参与算法一致性检查** | 用户改出与网格先验矛盾的图形 | 属性面板显示 `node_distance_m`；对远离任何格点的人工多边形标黄 |
| 5 | 编辑后重跑算法会覆盖人工修改 | 用户劳动丢失 | 编辑结果单独存 `edited_gaps`，重跑时提示"合并 / 覆盖 / 保留人工"三选一 |

**原型实测踩到的三个坑**（已修，写进 `desktop/README.md` 备查）：

1. `rasterio.windows.Window.intersection` 在**无交集时抛 `WindowError`**（不是返回空窗口）
   → 园区外瓦片每个请求都抛栈；
2. 本影像 **4 波段**（第 4 波段恒 255 = Alpha），把 4 个波段送进目标是 3 波段的

   必须 `--build-overviews` 建一次金字塔（写入约 1 GB 的 `.ovr` 边车文件，
   可随时删除重建）。这条也印证了架构文档 STEP 01「TIF 建金字塔」不是可选项。

## 8. 外部裁定结果（2026-10-17）

用户与外部架构顾问对齐后，对 §4 的待拍板问题给出正式裁定。

| # | 问题 | 裁定 | 依据 |
|---|---|---|---|
| 1 | 瓦片服务语言 | **保留 Python `tile_server.py`** | 建金字塔后 700~838 ms 已达标；避免 Rust / Python 双端链接 `gdal.dll` + `proj.db` 的冲突 |
| 2 | 地理内核归属 | **100% 保留 Python** | 52 个参数 + 参数指纹 + 95/95 契约测试 + 两台机器逐位一致；拆到 Rust 会破坏"可复现"红线 |
| 3 | 编辑合并策略 | **两档：保留人工（默认）/ 完全覆盖** | 复用已有留痕字段（`edited` / `edited_by` / `original_class` / `source`）；新结果与旧人工要素 IoU>0.5 时重放删除/改判 |
| 4 | 打包分发 | **`--onedir` 或精简 `.venv` 进 `bundle.resources`，禁用 `--onefile`** | onefile 每次启动要把数百 MB 动态库解压到 `%TEMP%`，冷启动 6~10 s 且易被杀软误杀 |

### 8.1 退让距离：拍板 `0.5 m`（不是 2.0 m）

**几何账**：`open_patch` 的边界是周边存活油棕的**树冠叶尖外缘**（距树干约 4.0~4.2 m），
不是树干中心。所以"从多边形边界退让 R" ≈ 新苗距老树干 `4.2 + R` 米。
单行缺株带两侧树干相距 2×7.23 = 14.46 m，扣掉两侧冠幅 8.4 m 后净宽仅 5~6 m。

**实测 449 块 open_patch 的等效宽度（2A/P，UTM 49N 精算）**：
P10 **2.93** · P25 **3.79** · **P50 4.68** · P75 **5.73** · P90 **7.27** m
→ 过半连片空地是窄条。

| 退让 | 理论可排点块数（宽−2R>1 m） | 排坑实测 |
|---|---|---|
| **0.5 m（默认）** | **437 / 449** | **3,594 株** |
| 1.0 m | 398 / 449 | 3,009 株 |
| 1.5 m | 308 / 449 | 2,551 株 |
| 2.0 m | **189 / 449** | 2,152 株 |
| 3.0 m | 51 / 449 | 1,569 株 |

→ 2.0 m 会把最典型的"单行缺株带"整片判为不可种（实测 123 块排坑为 0）。
**已把前端默认值改为 0.5 m**，UI 保留 0.5 / 1.0 / 2.0 三档。

### 8.2 落地实现（两项）

**① 金字塔不再污染源文件**

外部建议"以只读模式打开再 build_overviews，GDAL 会自动生成外置 `.ovr`"——
**经实测在 rasterio 里不成立**：

| 尝试 | 结果 |
|---|---|
| `rasterio.open(path, 'r')` + `build_overviews` | ❌ `AttributeError: 'DatasetReader' object has no attribute 'build_overviews'` |
| `rasterio.open(path, 'r+')` + `build_overviews` | ✅ 成功，但**写进文件内部**（2,045,752 → 2,562,938 B，无 `.ovr`） |
| `rio overview` | ❌ 没有只读选项（帮助里只有 `--build` / `--ls`） |
| `gdaladdo -ro` | ✅ 支持，但本机未安装 GDAL CLI |

因此实现为 `--ovr-mode` 三档策略（**默认永不改源文件**）：

| mode | 行为 | 改源文件？ | 额外磁盘 |
|---|---|---|---|
| `auto`（默认） | 有 gdaladdo → 外置 `.ovr`；否则**复制副本**建内部金字塔 | **否** | 0 或约等于原图 |
| `copy` | 总是复制副本 | 否 | 约等于原图 |
| `gdal` | 强制外置 `.ovr`（无 gdaladdo 则报错） | 否 | 约 1/3 原图 |
| `inplace` | 就地写入（旧行为，需显式指定） | **是** | +1.19 GB |

实测验证：源文件体积与 mtime 均未改变，返回的是副本。

**② ROI 圈选裁剪（R-P0-11）已实现**

- `--roi` 支持 `.geojson` / `.kml`（KML 用标准库 `xml.etree` 解析，无新依赖）
- **瓦片级跳过**：`tiles_in_roi()` 在**读取栅格之前**过滤，圈外瓦片零磁盘 IO
- **像素级掩膜**：`process_tile` 内把圈外像素置为无效（与 `--forest-mask` 同构、方向相反）
- **grid_survey 保护**（外部顾问提醒的暗坑）：ROI 内瓦片 < `max(4, survey_samples×2)` 时
  采样**回退全图**，避免"只圈了一小块空地 → 里面没树 → 网格拟合失败"；检测仍限 ROI 内
- 输出元数据：新增 `roi_source` / `used_roi`（`kml_source` / `used_kml` 保留兼容）
- **指纹只在启用 ROI 时加入 `roi_path`**：既不污染无 ROI 的既有缓存（否则全量重跑 1,048 秒），
  也不会错误复用无 ROI 的瓦片结果
- `sidecar.py` 五处同步：参数表 / args 赋值 / 回显 / 指纹 / 日志事件

**A/B 验证（测试 ROI 覆盖园区中部 20.9% 面积，479,576 m²）**

| 指标 | 全量 | ROI 跑批 | 变化 |
|---|---|---|---|
| 瓦片数 | 528 | **121** | **-77%** |
| 总耗时 | 1,048.2 s | **399.9 s** | **-62%** |
| 圈外要素泄漏 | — | **0 个** | ✅ |
| `used_roi` / `roi_source` | false / null | **true / 已记录** | ✅ |

**精度核对（公平口径：把全量结果与 ROI 求交后再比）**

| 指标 | A：全量 ∩ ROI | B：ROI 跑批 | 差异 |
|---|---|---|---|
| 要素数 | 664 | 639 | -3.8% |
| 总面积 | 112,804 m² | 112,364 m² | **-0.39%** |
| 需补种口径 | 101,045 m² | 100,607 m² | **-0.43%** |
| 空地占 ROI 比例 | 23.52% | 23.43% | -0.09 pt |

> ⚠️ 初次对比曾出现 -13%，原因是**口径不公平**：A 用的是"与 ROI 相交的完整多边形"
> （含伸出圈外的部分）。与 ROI 求交后再比，差异降到 **0.39%** —— 说明 ROI 裁剪没有引入偏差。
>
> 另注：ROI 内网格勘察参数与全图略有不同（株距 8.25 vs 8.45、方位 0.33° vs 0.67°、
> 质量 0.640 vs 0.752），会导致**类别重分配**（`alley_gap` -14%、`open_patch` -7%），
> 但**面积几乎不变**（-0.39%）—— 与 10-17 方位角 bug 修复时观察到的规律一致。
