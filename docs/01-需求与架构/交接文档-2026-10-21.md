## 1. 今天做了什么（按重要性）

### 1.1 构建链路：从"手工"变成"全自动"

| 改动 | 解决的问题 |
|---|---|
| 打包流程补 **PyInstaller 阶段**（4/5） | 以前靠"先手工跑一次 ps1"，漏了就打出没有 Python 运行时的包 |
| Rust 判定改为 **cargo + rustc 双检** | 工具链下载中断时 `cargo` 能跑、`rustc` 报 `missing manifest`，旧检测误判"已就绪"，`tauri build` 在 `rust.rs:1145` panic |
| Rust 修复改为 `rustup toolchain install stable` | 旧逻辑只跑 `default`（只设默认、不补文件），对损坏无效 |
| **MSVC 硬门槛**（阶段 3 前阻断） | 以前只警告，用户白等几分钟才看到 `link.exe not found`；现在给下载地址 + 勾选项 + 体积 |
| 英文路径**自动装 Python/Node** | 以前只甩一个 URL；现在调 `scripts/install_prereqs_en.ps1`（用户级、免管理员） |
| `pause` 不再卡死 | 向导开头有 `pause`，被脚本自动调用时永久阻塞（实测有人等了 22 分钟，向导一步没跑） |
| 心跳文案改准 | 「仍在构建（链接阶段）」→「仍在构建安装包（Rust 编译 + NSIS 压缩，共约 10-20 分钟）」 |

### 1.2 桌面端：六个真 bug

| # | Bug | 根因 | 修复 |
|---|---|---|---|
| 1 | 安装包 286 MB | PyInstaller 无排除列表，把 torch(365MB)/cv2(111)/av(64)/pyogrio(48)/transformers(36)/matplotlib(14) 全打进包 | 加 `--exclude-module`，**286 → 72 MB** |
| 2 | 「端口 8765 被其它程序占用」误报 | ① `lib.rs` 用 `.lines().map_while(Result::ok)` 读 stderr，遇一个非 UTF-8 字节就**整体停止**，traceback 全丢；② `tileDiag.ts` 先判端口、后判退出码，服务崩溃后端口残留时误报 | ① `read_until` + `from_utf8_lossy`；② 先判 `exit_code != 0`，端口分支加 `exit_code == null` |
| 3 | 8765 被占时功能完全不可用 | 无端口回退 | `pick_backend_port()` 试 8765~8776；`ACTIVE_PORT` 存实际端口；前端 `ensurePort()` 跟随 |
| 4 | 换影像后直接跳「复核结果」+ 弹"结果没读到" | 后端 `set_data_paths` 只在 `gaps` 有值时更新；前端 `workflow.loaded` 仍 true → 步骤判定"检测已完成" | 后端：影像变了且没指定新结果 → `cfg.gaps = None`；前端：`onWizardDone` 里 `setGaps([])` |

| 6 | 心跳停不掉（构建完成后还在刷"仍在配置环境"） | `ensure_npm` 又起一个心跳，覆盖 `FG_SENT` | 已有心跳就复用，`FG_NPM_HB` 标记"只停自己起的" |

## 8. 晚间补修（家机，2026-10-21 19:00~）

公司机不具备打包条件（MSVC/Rust 修好但耗时长），晚间在家机拉取 15 个 commit 后
先做"能不能验"的检查，发现**两处会让验证假阴性的结构性问题**：

### 8.1 运行时"存在即就绪"→ Python 修复永远进不了包（坑 49）

`ensure_py_runtime` 判据是 `if exist <exe> goto :ready`。而 `desktop/runtime` 里的
exe 是 **10-19** 冻的，`desktop_entry.py` / `build_derived.py` 是 10-21 改的 ——
脚本会打印「[已就绪]」直接跳过，`[E4099]` 的修复根本不在包里。
（交接文档 §4 原写"会强制重建 py-runtime"，与代码实际行为不符，已订正。）

修法：`build_desktop_runtime.ps1` 加 `-CheckStale`（0 新鲜 / 1 过期 / 2 未打包），
比 exe 与 `scripts/*.py`（排除 `check_*`/`test_*`）+ `requirements.txt` 的
`LastWriteTimeUtc`；`ensure_py_runtime` 先问它，过期则重建，且「[过期]」与
「[缺失]」文案分开（存在但旧了 ≠ 被打没了）。

### 8.2 `.gitkeep` 被构建删掉又随 `git add` 提交（坑 50）

`7cc898c`（今日最后一个提交）把 `desktop/runtime/desktop_entry/.gitkeep` **删掉了** ——
它在打包清理 `desktop\runtime` 时被连带删除，随后一起进了提交。
后果：CI 在干净 clone 上 `tauri-build` 的存在性检查会失败（本地因有真产物而全绿）。
已恢复，并加两条防线：打包完成后自动补回 + `check_all.py` 第 10 层
「仓库卫生」用 `git ls-files --error-unmatch` 断言它仍被跟踪。

## 9. 晚间新增：P1 导入期金字塔体检（家机，2026-10-21 20:30~22:50）

### 9.1 为什么做

开发机上的 `WGR17-002.tif` 早有金字塔，所以本地一切正常。但**新电脑导入一张
刚出图的原始 tif 时**，低缩放级瓦片实测要 **104 秒**（z=13）/ 35 秒（z=15）——
用户会以为软件卡死直接关掉。这是"能不能给别人用"的生死门，不是锦上添花。

### 9.2 交付了什么

**用户看到**：影像没有金字塔时，地图顶部出现黄色横幅
「这张影像没有加速结构 · 缩放到远处会很慢（一屏可能要等 1 分钟以上）」
→ 点「建立加速结构」→ 确认框（说明要复制副本、需多少磁盘、约 3 分钟、不动原图）
→ 转圈 + 已用时计时器 → 完成后横幅消失。

**关键设计**（改之前先读这几条）：
- **不做假进度条**：gdaladdo / rasterio 都没有进度回调，画百分比就是骗人
- **失败态人话打头、原文降级**：`explainBuildError()` 把 5 类错误翻译成
  「这台电脑缺少一个可选的加速组件」这类句子，原文放进「技术细节（可复制）」
- **文案禁词**：`gdaladdo` / `ovr` / `copy` / `inplace` / `GDAL` 不许出现在界面上，
  `tests/overview.test.ts` 有源码级守卫（剥注释与 `className` 后扫中文行）
- **「以后再说」只在本会话有效**，不写 localStorage —— 下次该提醒还得提醒

**代码落点**：
```
scripts/tile_server.py     overview_plan() 磁盘预检 / ensure_overviews() 原子写入 / --overviews-only
scripts/test_overviews.py  42 条：迷你 tif 真跑 desktop_entry 转发链路
desktop/src-tauri/lib.rs   build_overviews / overview_plan 两个命令；Services 第 4 槽位
```

### 9.3 三条策略怎么选（实测取舍）

| 策略 | 改源文件 | 额外磁盘 | 前提 |
|---|---|---|---|
| **外置 `.ovr`** | 否 | ~1/3 | **需要 gdaladdo** ← 本机与打包态都没有 |
| 复制副本（默认） | 否 | ~1.5x | 无 |
| 就地写入 | **是，不可逆** | ~1.34x | 仅 `--ovr-mode inplace` |

⚠️ **不要为了 `.ovr` 去 bundle gdaladdo**：它自带的 GDAL DLL 与 rasterio 那份
容易撞版本，收益远小于风险。想用 `.ovr` 只能让用户自己装 GDAL。

### 9.4 两个已修的隐藏 bug（都值得记住）

1. **`AtomicBool` 防不住"关窗重开"**：它只活在本进程内存里。用户点「开始」→
   嫌慢 → 关窗 → 重开 → 再点一次，新进程的锁是全新 `false`（放行），
   而上一轮孤儿进程还在往**同一个 `.part`** 写 → Windows 下必撞
   `PermissionError: [WinError 32]`。
   **解药是"启动前先杀掉旧的"**，不是"再删一次 `.part`"（删只清垃圾，不消竞争）。
2. **复用分支漏清 `.part`**：copy 模式在"副本已存在且带金字塔"时提前 `return`，
   走不到清理 → "副本已建好 + 中断残留半截 `.part`" 会把一份完整副本大小的垃圾
   永久留在盘上（真机 4.7 GB）。

### 9.6 一个已知的小遗留

`build_overviews` 的子进程现在会登记进 `Services` 并在退出时 kill。
但 `derive`（生成 CHM/掩膜）**刻意不杀** —— 它正在写一份有用的产物，
让它跑完比留半个 CHM 好（检测读到半截 CHM 不报错，那才是灾难）。
代价是关窗后它会自己跑完再退出。这是权衡后的选择，不是遗漏。
