## 1. 项目信息

| 项 | 内容 |
|---|---|
| 项目名（snake_case） | `forest_gap_detection` |
| 中文名 | 油棕园空地智能检测系统 |
| 目标平台 | **Windows 桌面优先**（Tauri v2），架构预留 macOS / Linux |
| 技术栈（建议基线） | Tauri v2 (Rust) + React + TypeScript + MUI + Tailwind CSS；GIS 渲染 WebGL（如 deck.gl / maplibre）；AI 推理侧 Python 服务（PyTorch/ONNX Runtime），详见架构文档 |
| 仓库 | `D:/Project/AI/Forest Gap Detection`（当前仅 README，无代码） |

### 原始需求复述（用户原话）
> 创建一个新的桌面端 Tauri 应用。用于接受用户从无人机航拍中收集并生成的 tif 图像（通常约 3GB），由 AI 检测空地并生成 polygon 包围每个空地，输出 1 个 json。

### 需求基线修正与确认（基于 README 权威前提）
README 明确业务为**油棕种植园林地管理**，而非普通森林。据此对原始需求做如下修正/补全，**需用户确认**：

1. **业务域**：油棕园（palm oil plantation）补种管理。
2. **输入**：除 ~3GB TIF 正射影像（DOM）外，**还必须支持 KML 边界文件**，用于圈定作业范围、按园区/地块（block）切割与归属。
3. **"空地"分三类**（判定标准与难度不同，需分类输出）：
   - **A 类｜长期闲置地块**：大面积、连续、无树冠覆盖；
   - **B 类｜枯死/缺株孔洞**：小面积、零散、成排缺失（单株或数株）；
   - **C 类｜光照充足林间空隙**：由树冠间隙/光照形成的中小空隙。
4. **最终产出**：不止"一个 JSON"，还隐含**补种坐标图盘**（可下发种植队的补种点位/图斑清单）。

### 核心可行性结论（回答用户"可实现吗"）
**可实现**，且属于成熟技术组合的工程化落地。关键可行性依据与风险：
- 3GB TIF 不能整幅读入内存 → 采用**分块 + 影像金字塔（overview）+ 内存上限控制**，工程上可行；
- 树冠/空地检测属于遥感语义分割成熟场景 → 可用**开源分割模型微调**或**自研训练**，取决于是否有标注数据与 GPU；
- polygon 矢量化（mask → 栅格转矢量 → 简化/平滑 → 面积过滤）为 GIS 标准流程，成熟可靠；
- **主要风险**不在算法本身，而在 **① 是否有标注数据/GPU 训练条件；② 空地判定标准与最小面积阈值由谁定义；③ 精度验收指标**——这三点见 Open Questions。

## 2. 产品定义

### 2.1 Product Goals（3 个正交目标）

1. **可靠地"吃得下"超大影像**：让一台普通 Windows 工作站能够稳定导入并处理 ~3GB 级 TIF 正射影像（含 KML 范围裁剪），全流程不因内存溢出崩溃，且可断点续跑。
2. **准确地"找得出"空地并分类**：基于 AI 自动识别油棕树冠，分割出空地 polygon，并按 A/B/C 三类输出，配套面积、质心、置信度等结构化属性。
3. **可用地"交得出"补种成果**：在影像上可视化叠加 polygon 供人工复核/编辑，最终导出标准化 JSON（GeoJSON 兼容）及补种坐标图盘，可直接下发给种植队执行补种。

> 目标正交性：目标 1 解决**工程性能/稳定性**，目标 2 解决**算法准确度/业务分类**，目标 3 解决**结果可用性与交付**，互不重叠。

### 2.2 User Stories（3–5 条）

1. 作为**园区 GIS 技术人员**，我希望导入 KML 边界与 3GB TIF 正射影像后系统能自动完成分块与裁剪，以便不必手动切割大文件、也不必担心电脑卡死。
2. 作为**园区农艺/管理人员**，我希望 AI 自动检测出全部空地并区分"长期闲置 / 枯死缺株 / 林间空隙"三类，以便按优先级安排补种资源。
3. 作为**复核人员**，我希望在影像地图上看到 polygon 叠加，并能手动删除误检、修正漏检，以便交付结果可信。
4. 作为**种植队负责人**，我希望导出一份含坐标、面积、类别的补种清单（JSON + CSV/KML），以便直接下发到现场补种。
5. 作为**系统管理员**，我希望模型可替换、可断点续跑，以便后续迭代模型或处理超长任务时不需从头再来。

## 3. 技术规范

### 3.1 Requirements Pool（P0 / P1 / P2）

> 措辞约定：**must** = P0（必须有）、**should** = P1（应该有）、**could** = P2（可以有）。
> 括号内为可度量标准建议（**待用户确认**，见 Open Questions）。

#### P0 — Must have（MVP 必须）

| ID | 需求 | 可度量标准（建议） |
|---|---|---|
| R-P0-1 | **超大 TIF 导入与预处理**：支持 ~3GB 及更大 GeoTIFF 导入；采用分块（tiling）+ 影像金字塔（overview）+ 内存上限控制，禁止整幅读入 | 内存占用峰值 must ≤ 可配置上限（默认 4GB）；导入不崩溃；支持 BigTIFF |
| R-P0-2 | **KML 导入与范围裁剪**：解析 KML 边界，仅对边界内区域处理；支持多地块（多 polygon / MultiGeometry） | must 支持至少 1 个 KML 含 N≥10 地块；每个地块独立编号与归属 |
| R-P0-3 | **AI 空地检测**：油棕树冠识别 → 空地（gap）分割 | must 输出栅格 mask，覆盖率/召回率达标（阈值待定，见 OQ-6） |
| R-P0-4 | **Polygon 矢量化**：mask → 栅格转矢量 → 几何简化/平滑 | must 输出合法 GeoJSON Polygon/MultiPolygon，无自相交 |
| R-P0-5 | **面积/最小面积过滤**：按阈值过滤噪声小块 | must 支持可配置最小面积阈值（如 ≥50㎡，**待定**） |
| R-P0-6 | **空地分类**：按 A/B/C 三类打标 | must 每个 polygon 带 `class` 字段（idle/hole/gap） |
| R-P0-7 | **JSON 输出**：结构化结果文件 | must 为 GeoJSON 兼容，含 CRS、block_id、面积、质心、类别、置信度、补种点数估算 |
| R-P0-8 | **可视化复核**：影像上叠加 polygon，支持删除误检 | must 可缩放/平移；点击选中 polygon 查看属性；可删除 |
| R-P0-9 | **结果导出**：JSON + 至少一种补种清单格式 | must 导出 JSON；should 同时导出 CSV 补种清单（含坐标/面积/类别/补种点数） |

#### P1 — Should have

| ID | 需求 | 可度量标准（建议） |
|---|---|---|
| R-P1-1 | **GPU 加速推理**：可选使用 GPU | should 支持 CUDA；有 GPU 时全流程耗时 ≤ 无 GPU 的 1/5（**待定**） |
| R-P1-2 | **断点续跑**：任务中断后可恢复 | should 按地块/分块保存中间态，重启后从断点继续 |
| R-P1-3 | **模型可替换**：模型以插件/配置文件方式加载 | should 更换模型无需改代码，仅替换权重 + 配置 |
| R-P1-4 | **多格式导出**：Shapefile / GeoJSON / KML / CSV | should 至少额外支持 KML（与输入同源，便于 GIS 对接） |
| R-P1-5 | **polygon 手动编辑**：不仅删除，还可微调/合并/新建 | should 支持顶点拖动与新增 polygon |
| R-P1-6 | **补种点自动布点**：在 polygon 内按株距/行距生成补种点 | should 支持按种植规格（株行距）生成点位（规格**待定**） |
| R-P1-7 | **全流程进度与日志** | should 底部进度条 + 可导出日志 |

#### P2 — Could have

| ID | 需求 | 可度量标准（建议） |
|---|---|---|
| R-P2-1 | **人工标注工具**：用于产出训练数据 | could 内置或对接标注工具（如 LabelMe/CVAT 流程） |
| R-P2-2 | **多影像/多期对比**：历史影像比对识别新空地 | could 支持多期 DOM 叠加对比 |
| R-P2-3 | **精度评估报告**：自动产出混淆矩阵/IoU | could 基于验证集输出 mIoU/Precision/Recall 报告 |
| R-P2-4 | **批量任务队列**：多个 TIF 排队处理 | could 支持任务队列与定时批处理 |
| R-P2-5 | **macOS / Linux 支持** | could 跨平台打包（架构预留即可） |

#### 关键技术说明

- **性能预期（待确认）**：3GB 影像全流程耗时目标——建议无 GPU ≤ 60 分钟、有 GPU ≤ 15 分钟（**待用户拍板**，见 OQ-6/OQ-8）。
- **模型来源（待确认）**：两条路线——(a) 微调开源遥感分割模型（如基于 U-Net/SegFormer/DeepLab 的遥感权重）；(b) 自研训练（需标注数据 + GPU）。取决于 OQ-1/OQ-2/OQ-3。
- **坐标系/投影（待确认）**：需支持从 TIF 的 CRS 读取，KML 为 WGS84（EPSG:4326），需做投影转换（见 OQ-9）。

### 3.3 UI Design Draft（主界面布局，文字描述）

采用经典 GIS 桌面应用三栏布局：

- **顶部工具栏（Toolbar）**：导入 TIF / 导入 KML、开始检测、暂停/续跑、导出（JSON/KML/CSV）、设置（模型、阈值、CRS）。
- **左侧面板（任务 / 图层列表）**：任务列表（多地块/多任务）+ 图层控制（影像图层、polygon 图层按类别开关、透明度）。
- **中间画布（Map Canvas）**：影像地图画布，WebGL 渲染，支持缩放/平移；polygon 叠加显示（A/B/C 三类用不同颜色），可点击选中、删除、编辑。
- **右侧面板（属性面板）**：显示选中 polygon 的属性（编号、类别、面积、质心、置信度、补种点数），支持修改类别/删除。
- **底部（状态栏 / 日志）**：全流程进度条、当前阶段（导入/裁剪/推理/矢量化/导出）、可滚动日志。

### 3.4 Open Questions（**必须由用户拍板**，直接影响架构选型）

> 以下问题未闭环前不建议进入开发；请用户逐条答复。

**AI 模型与数据（最高优先级，决定算法路线）**

**判定标准（决定算法后处理与验收）**
4. **"空地"的最小面积阈值与三类判定标准由谁定义？** 三类（闲置/孔洞/林间空隙）的面积区间、形状、上下文规则是什么？—— 直接决定 R-P0-5/R-P0-6。
5. **补种株数与布点规格？** 是否按固定株行距生成补种点？规格（如 9m×9m）是多少？—— 决定 R-P1-6 与 `estimated_replant_points` 算法。
6. **精度验收指标？** 有无明确的 mIoU / Precision / Recall / 面积误差目标？由谁验收？—— 决定 R-P2-3 与项目成败标准。

**部署与集成（决定架构边界）**
7. **是否需要联网/离线？** 是否允许云端推理，还是必须纯离线本地运行？（涉密/数据安全？）
8. **性能预期？** 3GB 影像全流程可接受的耗时上限是多少？是否必须 GPU？
9. **园区坐标系/投影？** 常用 CRS 是哪种（EPSG 代码）？KML(WGS84) 与影像 CRS 转换是否已明确？
10. **是否有 GIS 系统对接需求？** 是否需对接 ArcGIS/QGIS/自有平台？交付格式除 JSON 外是否必须 Shapefile/KML？
11. **单机还是多机/团队协作？** 是否需要多人共享结果、集中存储、权限管理？
12. **平台范围？** 是否只做 Windows，还是必须支持 macOS/Linux？（当前假设 Windows 优先）
13. **TIF 规格细节？** 影像波段数（RGB/多光谱）、位深、是否含地理坐标、单文件还是分幅？—— 影响导入与预处理实现。
14. **KML 结构？** 单个 KML 是单地块还是多地块？地块层级（园区→分区→地块）如何组织？

## A.1 变更原因（用户澄清原话摘要）

用户在评审 v0.1 后提出三点澄清，直接改变了需求范围：

1. **关于 TIF 是什么**：用户质疑"TIF 通常指 GeoTIFF（带地理标记的图像），为什么把它叫影像？它不是图片吗？"——说明需要统一"影像 = 带地理坐标的图"这一基础认知（术语科普见 `docs/glossary-for-beginners.md`）。
2. **【核心】检测目标大幅收敛**：用户明确——"**只需要标出空地/空隙就行了，枯死不需要在意**；也**不需要区分长期闲置与枯死**；业务本质**只需要 1 个类（空地）**，不需要很多类；**也不在意时间维度**（不关心长期还是短期空置，只关心**哪些土地还是空置的**）"。
   - 同时抛出一个**可选增强设想**："如果能同时分类出'正常 / 林间空隙 / 枯死缺株'，可以考虑把项目优化成能同时检测这两类并输出 JSON。"
3. **关于分类与 KML 的疑问**：用户认为 README 需求不准（自己也在摸索），并反问——"**为什么'空地'要分三类（idle/hole/gap）？不是只需要区分是不是空地吗？**"；同时问"**KML 是刚需吗？** README 说是基于 KML，但最终用户说是基于无人机航拍的 tif，到底哪个格式才对？"

**主理人判定结论**：① 检测目标收敛为**单类「空地」**；② **KML 由刚需降级为可选**；③ "林间空隙 vs 枯死缺株"二分类**降级为 P2 可选增强**。

| # | 维度 | v0.1 原需求 | v0.2 新需求 | 影响范围 |

| C-3 | **KML 地位** | **P0 刚需**，必须导入并据此裁剪、切分地块 | **P1 可选**。KML 与 TIF **不是二选一**：TIF 是**数据**，KML 是**范围**。**无 KML → 整幅影像视为单个地块（single block）；有 KML → 按地块切分** | 导入流程、任务切分、`blocks[]` 结构（无 KML 时用单 block 承载）、UI、Open Questions |
| C-4 | **补种分类优先级** | 三类按优先级安排补种资源 | **不再分类**，直接输出全部空地即可 | User Story、UI 属性面板、导出清单 |
| C-5 | **"林间空隙 vs 枯死缺株"二分类** | 与主检测同级（P0） | **降为 P2 可选增强**，通过「株行距网格」结构先验实现（架构师论证中）。数据模型**保留 `class` 字段**以便将来启用 | 模型设计（预留多类能力）、JSON schema（保留 `class`/`class_confidence`/`class_method`） |
| C-6 | **术语与沟通** | 未提供科普材料 | 新增面向 junior/实习生的**术语科普文档** | 文档交付物（`docs/glossary-for-beginners.md`） |

## A.3 修订后的 Product Goals（3 个，正交）

1. **吃得下**：让一台普通 Windows 工作站能稳定导入并处理 ~3GB 级 GeoTIFF 正射影像，**无论有无 KML** 都能跑通（无 KML 时整幅作为单地块），全流程不因内存溢出崩溃且可断点续跑。
2. **找得准**：基于 AI 自动识别油棕树冠，**输出单类「空地」的 polygon**（二值：树冠 / 非树冠），配套面积、质心、置信度等结构化属性，不再分类、不涉时间维度。
3. **交得出**：在影像上可视化叠加 polygon 供人工复核/编辑，导出标准化 JSON（GeoJSON 兼容）及可选的补种点位清单，直接下发种植队。

> 正交性：目标 1 = 工程性能/稳定性；目标 2 = 算法准确度（单类）；目标 3 = 结果可用性与交付。三者互不重叠。相比 v0.1，**目标 2 从"准确分类"简化为"准确找空地"**。

## A.5 修订后的输出 JSON Schema（单类版）

**变更要点**：去掉 `idle/hole/gap`，`class` 字段**保留但值固定**；保留 `class_confidence` / `class_method` 作为将来升级（P2）预留；`blocks[] → gaps[]` 嵌套结构**保留**（无 KML 时用单个 block 承载）；其余字段（`area_sqm` / `centroid` / `confidence` / `replant_points` / `summary`）不变。

```json
{
  "schema_version": "0.2",
  "crs": "EPSG:32648",
  "source_image": "block_A_ortho.tif",
  "kml_source": null,
  "generated_at": "2025-10-12T00:00:00Z",
  "model": { "name": "palm_canopy_seg", "version": "0.2.0", "type": "semantic_segmentation" },
  "blocks": [
    {
      "block_id": "B0001",
      "block_name": "Whole Image",
      "gaps": [
        {
          "gap_id": "B0001-0001",
          "class": "vacant",
          "class_confidence": null,
          "class_method": "single_class",
          "geometry": { "type": "Polygon", "coordinates": [[[x, y], [x, y], [x, y], [x, y]]] },
          "area_sqm": 123.4,
          "centroid": [x, y],
          "confidence": 0.92,
          "estimated_replant_points": 3,
          "replant_points": [[x, y], [x, y], [x, y]]
        }
      ]
    }
  ],
  "summary": {
    "total_gap_count": 128,
    "total_area_sqm": 45678.9,
    "by_class": { "vacant": 128 }
  }
}
```

**字段约定**：

| 字段 | 类型 | v0.2 取值/说明 |
|---|---|---|
| `class` | string | **固定为 `"vacant"`**（= 空地）。保留字段，为将来 P2 启用 `"gap"`（林间空隙）/`"dead"`（枯死缺株）预留 |
| `class_confidence` | number \| null | v0.2 单类阶段为 `null`；P2 启用二级分类后填分类置信度 |
| `class_method` | string | 取值 `"single_class"`；P2 升级后可为 `"planting_grid_prior"` |
| `kml_source` | string \| null | 无 KML 时为 `null`，此时 `blocks` 仅含 1 个整幅 block |
| `blocks[]` | array | 无 KML = 1 个 block（整幅）；有 KML = N 个 block（按地块） |
| `summary.by_class` | object | v0.2 仅含 `vacant` 键；P2 后可含 `gap`/`dead` |
| 其余字段 | — | 与 v0.1 一致，**不变** |

> 备选：`class` 也可固定为 `"gap"`。**建议采用 `"vacant"`**，语义更贴近"空地"，且避免与 P2 的"林间空隙(gap)"命名冲突。最终以用户确认为准（见 A.6-Q3）。

# 附录 B：v0.3 变更（2026-10-13）

> 本附录记录 v0.2 之后在**真实影像实测**基础上发生的变更。A 篇保留为历史，
> 以便追溯"为什么当初这么定"。**凡与 A 篇冲突之处，以本附录为准。**

## B.1 为什么要改

A 篇（v0.2）的结论建立在"尚未见到真实影像"的前提下。拿到 WGR17.tif 实测后发现三个事实，
迫使模型从"单类二值"演进为"四类分类"：

| # | 实测发现 | 对模型的影响 |
|---|---|---|
| 1 | 空地**形态差异极大**：单株位缺株约 40~60 m²，而区块间成片空地可达数千 m² | 「一刀切算空地」会产出大量无意义的"整片都要补种"结论 |
| 2 | 园区有**清晰的株行距网格**（株距 8.35 m、行距 7.23 m、错行角 60°、密度 165.6 株/公顷），质量 0.734 可用 | 让「株位空缺」成为**可判定**的几何问题，不再需要机器学习 |
| 3 | 树冠**粘连严重**，纯分位判据在密植区整片误判（v1 误报全园 18%） | 需要混合判据 + 结构化后处理（见 `03-算法教学/分割判据说明.html`） |

## B.2 类别定义（四类，取代 A 篇的单类 `vacant`）

| 常量 | 中文标签 | 语义 | 是否需补种 |
|---|---|---|---|
| `CLASS_VACANT_SLOT` | 株位空缺 | 单个株位缺一株，面积中位 59 m² | ✅ 补 1 株 |
| `CLASS_ALLEY_GAP` | 林间空隙 | 树冠之间的正常缝隙（株间必修的通道） | ❌ 无需补种 |
| `CLASS_OPEN_PATCH` | 连片空地 | 跨多个株位成片，面积 30 m² 至数千 m² | ⚠️ 需按网格整片补种，**但见 B.3** |
| `CLASS_UNCERTAIN` | 不确定 | 证据不足，交人工复核 | ❓ 人工判断 |

**分类方法**：证据打分（`c_slot` / `c_patch` / `c_alley` 三个独立证据强度），
而非硬 if-else 链——避免在容差边界上抖动。`class_method = "planting_grid_prior"`。

## B.3 ⚠️ 关键业务口径：道路 / 排水预留带不算补种地（2026-10-13 用户确认）

**这是本轮最重要的一条需求变更。**

实测数据显示：`open_patch` 共 **380 块、合计 23.6 万 m²，占全部空地面积的 74%**。
这些空地**形态异常规整**——面积大、边界直、成条带分布，位置恰好落在种植区块之间。

**用户判定**：这类区域是园区**本来就规划好的道路或排水沟预留带**，
属于"设计如此、不该种树"，**不应计入需补种的空地**。

> 用户原话确认：「道路 / 排水预留带不算『要补种的地』」

### 影响与待办

- **当前算法不区分**这类区域，仍会把它算进 `open_patch`。**这是已知偏差**，
  在它被解决前，**"需补种 380 片 / 23.6 万 m²"这个数字不可直接使用**。
- 解决方式待定（两条路，尚未实现）：
  1. **几何自动排除**：按形状（长条、笔直、宽窄均匀）识别并单独归类
  2. **外部矢量扣减**：由用户提供道路/排水沟矢量图，在输出前扣减
- 建议新增类别 `CLASS_RESERVED_BAND`（预留带），或复用 `uncertain` 并加标记字段。
  **决策前不要动代码**，避免返工。
