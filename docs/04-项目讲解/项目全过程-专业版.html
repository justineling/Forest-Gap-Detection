01项目定位

一个桌面应用：输入无人机正射影像，输出可执行的补种坐标清单。

做什么

从航拍正射影像中自动识别没有油棕树冠覆盖的地面，矢量化为多边形，输出 GeoJSON。

给谁用

种植园管理者 / 补种作业队。他们要的是一张"哪里缺树、缺几株"的作业图。

为什么做

人工巡园靠走，229 公顷要走很久且容易漏。航拍 + 自动识别能把巡园变成一次性批处理。

📌

需求收敛的关键一步

原始需求提到要区分「长期闲置 / 枯死缺株 / 光照林间空地」三类。经澄清后确认：业务只关心单一类别「空地」——哪些土地还空着。不区分是否枯死，不涉及时间维度。

这个收敛极大简化了方案：从"多类分类问题"变成二值判定问题（树冠区域 vs 非树冠区域）。

02输入输出契约

先把边界定死，后面的所有设计都围绕它展开。

输入

项要求实测值（WGR17.tif）
影像格式GeoTIFF / BigTIFF，含地理坐标BigTIFF，4 波段 8 位
坐标系任意，需可转换EPSG:4326（经纬度）
尺寸数 GB 级47,130 × 44,686 = 21.06 亿像素 / 3.5 GiB
地面分辨率优于 10 cm/px3.30 cm/px
波段RGB 可接受RGB + Alpha（无近红外）
KML 范围可选（P1）本次未提供 → 整幅视为单 block
⚠️

坐标系是必须处理的第一道坎

影像的 CRS 是 EPSG:4326，单位是"度"。在这种坐标系下算出来的"面积"没有物理意义。

因此所有面积、质心、距离计算一律先重投影到 EPSG:32649（UTM 49N，单位米）。这是硬约束，写在工程约定里。

输出

GeoJSON（schema_version = "0.3"），嵌套结构 blocks[] → gaps[]，字段 snake_case。

03架构选型

桌面优先、Windows 优先，但架构预留跨平台。

三组关键取舍

决策点选择理由
桌面框架 Tauri v2 相比 Electron，安装包小一个数量级；Rust 侧可直接调 GDAL/PROJ，省掉跨进程地理计算
推理落地方式 Python sidecar（ONNX Runtime） Python 生态的模型工具链最全；ONNX 分发避免把 PyTorch 打进安装包（体积风险）
大影像处理 COG + 窗口化 + 金字塔 3.5 GiB 影像不可能整幅读入内存，必须按需读窗口
💡

为什么 Python 用 sidecar 而不是嵌入

模型迭代频繁（换权重、调后处理），放在独立进程里可以单独升级而不重编 Rust。同时推理崩溃不会带崩主界面。代价是多一层进程间通信与打包复杂度。

05关键工程决策

这些决策不是"最佳实践"，而是被实测问题逼出来的。

① 瓦片重叠 + 质心归属

不这么做会怎样

恰好跨越瓦片边界的空地会被切成两块，各自面积都不到阈值，两边都丢掉——最终结果里凭空少一块空地。

做法

每块向外多读 overlap=128px（≈4.2 m，大于半株距）；输出时只保留质心落在本瓦片核心区的多边形。跨边界的空地只会被"它质心所在的那块"输出一次。

② 全局网格而非逐块网格

株行距网格的相位必须全局一致。如果每块各自估计、各自定原点，相邻瓦片的格点会错开半格，同一块空地在两块里会被判成不同类别。

做法：先跑一遍网格勘察，在若干采样瓦片上估计后取中位数，得到全局网格；之后所有瓦片共用这一个网格。

③ 断点续跑 + 参数指纹

整幅 229 公顷、528 个瓦片，跑一遍约 20 分钟。中途断电不该从头再来。

机制实现防的是什么
原子写盘 先写 .tmp 再 os.replace() 中途断电留下半个损坏的 JSON，下次读进来直接崩
参数指纹 影像（路径+size+mtime）+ 全部参数 → SHA256 前 16 位 改了参数却拿到旧结果——这是最坑的情况
有效性排序 order_tiles_by_validity() 用金字塔概览排序 园区只占外接矩形 57%，行优先遍历开头全撞 NoData
🧪

实测验证

同命令重跑 → 显示「命中缓存 5，新处理 0」，结果完全一致。
改一个参数（--min-area 30 → 60）→ 指纹从 67d1c4a2 变为 333d2152，缓存全部失效重算。

④ 用距离变换替代形态学暴力卷积

空地分离原本用 scipy.binary_opening(mask, disk(r=24))。圆盘结构元是 O(r²) 的暴力卷积——2304² 上每像素要算约 1800 次比较，单块 11.7 秒，占整条流水线 85% 的时间。

改用距离变换实现等价的圆盘开运算（O(n)）：1.95 秒，快 6 倍。实测差异像素仅 0.04%，且 99.4% 落在数组边界 40px 内——而边界本来就会被 overlap 机制丢弃。

🚫

一个不能走的捷径

不能用 binary_opening(mask, np.ones((3,3)), iterations=r) 代替——那构造出来的是菱形而不是圆盘，实测差异 46,092 个像素，会改变结果形状。

06算法方案

核心思路一句话：只训练"认树"，空地 = 树冠掩膜的补集。

为什么不用深度学习模型

项目初期下载了 DeepForest 预训练权重（MIT 许可）准备做树冠检测。实测结论：不可用。

指标DeepForest 预训练期望值结论
检测置信度（中位）0.400.7 ~ 0.95模型对每个判断都没把握
冠层覆盖率39.0%60 ~ 80%漏检约一半树冠
框宽中位5.73 m7 ~ 9 m尺寸偏小且不稳定

根因是域偏移（domain shift）：训练数据是北美 NEON 温带森林，与油棕园在树冠形状、种植规律性、背景色、分辨率上全都不同。

采用的方案：冠层结构法

ExG = 2·G − R − B                          # 超绿指数
sm  = 高斯平滑(ExG, sigma=5)                # 把同一株的羽叶连成一片
thr = clip(percentile(sm, 40), 40, 80)      # 混合阈值
canopy = (sm > thr) | (饱和度 > 0.45)        # 高饱和度兜底判为植被
canopy = 闭运算×3 → 开运算×2 → 填洞 → 去 <2000px 碎块
gap    = ~canopy & valid                    # 补集
gap    = 圆盘开运算(gap, r=24px)             # 分离连通缝隙网络
gap    = 去 <200px 碎块

阈值判据的演进（三次迭代）

版本判据实测问题
v1 纯分位 40% 相对判据，把健康林下植被整片误判成空地（全园 18% 被标空地）
v2 纯绝对 ExG > 60 对曝光过敏。跨航带 ExG 中位差 3 倍，暗航带冠层只剩 31%
v3 混合 clip(分位40%, 40, 80) + 饱和度辅助 跨曝光稳定：密植区 88% / 中南 79% / 中央 67%，落在合理区间
⚠️

评估时的隐藏陷阱

算"冠层覆盖率"时必须先掩掉 NoData。影像外接矩形里有大片空白区（园区只占 57%），不掩的话会把 NoData 算进分母。实测某瓦片全图冠层 31%、仅有效区 71%——差一倍多，足以得出完全相反的结论。

空地分类（4 类）

类别含义判定依据实测中位面积
vacant_slot 株位空缺单个株位缺一株质心贴近格点 + 形状不细长 + 面积约一格59 m²
alley_gap 林间空隙树冠间正常缝隙细长 / 面积远小于一格 / 明显夹在两行之间52 m²
open_patch 连片空地跨多格成片空缺面积 ≥ 2 个单位格且形状证据不足321 m²
uncertain 不确定证据不足，人工复核各项证据均不充分93 m²

分类用证据打分而非硬 if-else 链，避免在容差边界上抖动（同一块空地在不同瓦片里因相位误差被判成不同类）。

07能力边界

必须如实区分：什么能承诺，什么不能。

高可信 · 可承诺

「有没有树冠覆盖」

几何判定，跨曝光稳定。这是产品的核心承诺。

中等可信

「株位空缺 vs 林间空隙」

靠株行距网格先验。失效条件：种植不规则 / 缺株率 > 30~40% / 行随地形弯曲 / 树冠严重粘连。

不可辨识 · 不可承诺

「是否枯死」

单张影像不含"这棵树曾经活着"的历史信息——这是物理观测的极限，不是算法不够好。

❗

产品定位必须与能力对齐

UI 上应把分类结果标注为「候选类别，需人工确认」，而不是"系统判定结果"。若业务确实需要区分枯死，必须补充多期影像 / 多光谱 / DSM——这属于需求变更，不是调参能解决的。
