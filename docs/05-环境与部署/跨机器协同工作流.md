# 跨机器协同工作流

> 适用场景：同一个人在**两台及以上电脑**上开发本项目（如公司机 + 家用机）。
> 本文约定「什么通过 git 同步、什么通过网盘同步、分支怎么用、日常怎么操作」。
> 最后更新：2026-10-14

---

## 一、同步分工：哪些东西走哪条路

| 内容 | 路径 | 同步方式 | 说明 |
|---|---|---|---|
| 源码 | `scripts/` | **git** | 必须同步，否则两台机器行为不一致 |
| 文档 | `docs/` | **git** | 含 HTML 报告、Markdown |
| 项目记忆 | `.workbuddy-ai/memory/` | **git** | 长期约定 + 每日日志，跨机器共享上下文 |
| 交接文档 | `交接文档-*.md` | **git** | |
| 临时产物 | `.workbuddy-ai/tmp/` | ❌ **不同步** | 一次性诊断脚本与中间图，已 gitignore |
| 检测结果 | `output/` | **Google Drive** | 6.6 MB 且每次全量变，不适合进 git |
| 模型权重 | `models/` | ❌ **不同步** | 体积大，由 `配置环境.ps1` 重新获取 |
| Python 环境 | `.venv/` | ❌ **不同步** | 每台机器各自 `一键配置环境.bat` 生成 |

### 为什么 `output/` 不进 git

- 单次全量 GeoJSON 就有 6.6 MB，且**每次重跑内容全变** → git 无法有效增量存储
- 二进制大文件反复提交会让仓库迅速膨胀（对比：把 `.workbuddy-ai/tmp/` 误纳管
  就贡献了 16.9 MB，`.git` 一度膨胀到 50 MB）
- **改用 Google Drive**：把 `output/` 目录放进一个 Google Drive 同步文件夹，
  两台机器都能看到最新结果

> ⚠️ 注意：`output/` 是**运行产物**，随时可以被重跑覆盖。
> 跨机器取用时，先确认时间戳，避免拿到旧结果。
> 本机重跑一次约 **57 分钟**（4 核 CPU），家里那台约 16 分钟——**CPU 核心数是主因**。

## 二、分支模型：主干开发（Trunk-Based Development）

### 采用的结构

```
main                                  ← 唯一长期分支，始终可发布
  ├─ feat/<topic>                     ← 短命特性分支（几天内合回）
  ├─ fix/<topic>
  ├─ docs/<topic>
  └─ chore/<topic>
```

**约定**：

1. `main` 是唯一长期分支，**始终处于可用状态**（测试通过、能跑通）
2. 一切改动都走短命分支，命名格式 `<类型>/<简短主题>`，类型用
   `feat` / `fix` / `docs` / `chore` / `refactor`
3. 分支**做完就合回 `main` 并删除**，存活时间以「天」为单位，不要以「周」计
4. 合回 `main` 前必须：跑通契约测试（`test_sidecar_contract.py` 期望 **95/95**）
5. 提交信息用中文 + Conventional Commits 前缀

### ❌ 不要用的做法：每台机器一个长期分支

曾经考虑过 `dev-a` / `dev-b`（一台机器一个长期分支）。**这是反模式**：

| 问题 | 说明 |
|---|---|
| 分支语义错位 | 分支应该表达**工作**，不是**机器**。机器是执行环境，不是版本维度 |
| 合并地狱 | `dev-a` / `dev-b` 各自偏离 `main` 越久，合并冲突越多、越难解 |
| 合并面翻倍 | 变成 `feat → dev-a → main`，多一道合并 |
| 违背分布式设计 | git 本就是分布式的，同一个分支可以在两台机器上都存在 |

**真正要解决的是「两台机器怕互相覆盖」，而这靠操作习惯解决，不靠分支结构**：
开工前 `git pull`，小步提交，每个逻辑单元就 `push`。

## 三、日常操作流程

### 开工前（每台机器都要做）

```bash
git switch main
git pull                      # 先同步，避免基于旧代码开工
```

### 开始一项工作

```bash
git switch -c feat/<主题>      # 从最新的 main 拉出
# ...改代码...
.venv/Scripts/python.exe scripts/test_sidecar_contract.py   # 期望 95/95
git add -A -- <明确的路径>
git commit -F - <<'EOF'
feat(范围): 中文简述

详细说明改动内容与验收结果
EOF
```

### 收工前

```bash
git push -u origin feat/<主题>   # 推上去，另一台机器/远端才有备份
```

### 合回 main

```bash
git switch main
git pull
git merge --no-ff feat/<主题>
git push
git branch -d feat/<主题>
```

> 📌 本项目约定：**合回 `main` 前需经用户确认**。

## 四、`output/` 用 Google Drive 同步的具体做法

1. 在 Google Drive 里建一个文件夹，例如 `ForestGapDetection-output`
2. 在本机把它挂载/同步到本地（Google Drive 桌面版会给一个盘符或本地路径）
3. 让 `output/` 指向它，或每次跑完手动复制过去：

```bash
# 跑完检测后，把结果同步到 Google Drive 目录
cp -r output/arcgis/* "/path/to/Google Drive/ForestGapDetection-output/arcgis/"
cp output/wgr17-full-gaps.geojson "/path/to/Google Drive/ForestGapDetection-output/"
```

4. 另一台机器从 Google Drive 取用前，**先比对 `generated_at` 字段**确认版本：

```bash
.venv/Scripts/python.exe -c "import json;d=json.load(open('output/wgr17-full-gaps.geojson',encoding='utf-8'));print(d['generated_at'], d['summary']['total_gap_count'])"
```

## 五、Git 红线（违反会返工）

1. **绝不自动 commit** —— 完成工作后先汇报，得到用户明确同意才提交
2. ⚠️ `git stash pop` 恢复的文件是 **staged** 状态，此时裸跑 `git commit`
   会把它们一并卷进去。提交前先 `git reset` 清空暂存区，再按路径 `git add`
3. ⚠️ **不要相信本地 `origin/main` 跟踪引用**（`git rebase` / `checkout` 会顺带更新它，
   导致 `git status` 谎报 "up to date"）。核实远端真实状态必须用
   `git ls-remote origin refs/heads/main`
4. 提交信息用**中文** + Conventional Commits 前缀

```bash
git clone <仓库地址>
cd "Forest Gap Detection"
# 1) 建 Python 环境（双击即可，会自动装依赖到 D 盘）
一键配置环境.bat
# 2) 环境体检（生成 05-环境与部署/环境检测报告-<机器名>.md）
环境体检.bat
# 3) 验证基线
.venv/Scripts/python.exe scripts/test_sidecar_contract.py   # 期望 95/95
# 4) 大影像 WGR17.tif 需另行获取（3.5 GB，不在仓库里）
# 5) output/ 从 Google Drive 取用，或本机重跑
```
