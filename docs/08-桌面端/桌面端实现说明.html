桌面端实现说明（专业版）

Forest Gap Detection · Tauri v2 + React 18 · 2026-10-21 ｜ P0–P2 + 验证集（Q1）+ 导入期金字塔体检（P1）全部完成

一句话：把「跑一遍算法、看一个 GeoJSON」变成「双击装包、圈一块地、350 秒出 21 件可直接交付的文件」。 本文只讲为什么这么设计；踩坑清单在 desktop/README.md（45 条，每条带错误原文）， 操作步骤在 桌面端使用手册.md。

1. 五步工作流

② ④ 可跳过（跳过有代价），① ③ ⑤ 必做 —— 顶部工具栏与右下角卡片就是按这五步组织的

2026-10-19：工具栏按这五步收敛了。 改之前是 14 个平铺按钮（影像状态 / 载入结果 / 数据 / 撤销 / 重做 / 圈选 / 导入范围 / 清除 / 框选 / 开始检测 / 参数 / 新增空地 / 估算 / 导出），用户看不出该点哪个。 现在 header 只有「品牌 + 五步进度条 + 影像灯 + 撤销 / 重做 + ⋯ 更多」， 高频动作全部搬进地图右下角的「下一步」卡片（任何时刻只有 1 个主动作）， 低频动作（换数据 / 参数 / 补画 / 估算 / 日志）收进「⋯ 更多」。 状态机在 desktop/src/lib/workflow.ts，有 45 项单测。

2. 进程模型：三个进程，各管一段

桌面端不是一个"大 Python 程序加个壳"，而是三个进程各有明确边界。 这条边界是 2026-10-17 就冻结的技术决策，P0–P2 没有改动它。

只有瓦片走 HTTP（MapLibre 必须能用 URL 取图）；检测走 stdio，不经过网络

2.1 为什么检测不走 HTTP

  • 契约已冻结并通过 95/95 测试，改传输方式等于重写一遍；
  • stdio 是逐行流式的，进度事件天然实时；HTTP 还得再设计一套推送；
  • 不占端口 —— 用户同时开两个实例不会互相抢 8765。

2.2 一条硬约束：必须两个线程分别读 stdout 与 stderr

Windows 匿名管道缓冲区只有 64 KB。跑批时每个瓦片都往 stderr 写日志， 若只读 stdout、打算"等进程结束再读 stderr"，缓冲区很快填满 → Python 的 log() 阻塞在 write 上 → 整个 sidecar 永久卡死。

症状极具误导性：进度条停在 30%、CPU 归零、没有任何报错。 修法是 spawn 之后立刻起两个线程，各自 BufReader::lines() 并 emit 到前端。

3. 检测面板：把"会算错"提前成"不让开始"

P0 之前，点「开始检测」会直接把参数交给 sidecar。问题是：其中 4 个是文件路径， 缺了不会报错 —— sidecar 只回一条 W1004 就照常跑完， 结果退化成"纯 RGB"。用户在 350 秒后拿到一份看着正常、语义全错的数据。

更严重的一个：前端从来没传 forest_mask_path， 桌面端结果一直包含未开发林 —— 正是那个"多算 221 个放样点"的问题原样复现。

用户在引导里选了 E:\BlockB\ortho.tif，那两个写死成相对路径的 output/chm.tif / drone data/segment.tif 永远找不到。 预检按四级顺序搜索：

影像同目录  →  影像/output  →  数据基准  →  数据基准/output

命中就写回 resolved，run_detect 拿到的是绝对路径。 告警文案也从"文件不存在"改成"在影像同目录与 output/ 下都没找到 chm.tif"—— 用户知道该把文件放哪。

3.3 进度条

字段严格对齐 sidecar 的 progress 事件：done / total / ratio / elapsed_s / eta_s / gaps_found / gap_area_sqm。 两个不显眼但会致命的细节：

  • 合并用 ?? 不用 || —— done=0 是合法值（第一块还没完成）， 用 || 会让进度条永远不动；
  • 还没拿到 total 时走"来回扫"动画，避免停在 0% 让人以为卡死。

4. 复核三件套：让用户"敢改"

1,726 个多边形里有 465 块 uncertain（待复核）。原来的界面里 "这一片都是误报"只能一块一块点，删错了还无法恢复 —— 用户实际不敢动手。

4.1 撤销栈的六个决定

项决定理由
存储快照 gaps.slice()要素对象不可变 → 结构共享，约 14 KB/步
上限40 步40 × 14 KB < 1 MB，够用且不失控
批量一次操作 = 一步否则框选 40 块删除要按 40 次 Ctrl+Z
新操作清空重做栈否则时间线分叉（撤销→改别的→还能重做回旧分支）
拖拽1.5 s 时间窗合并TerraDraw 每移动几个像素发一次 change，不合并会吃光栈
换数据setGaps 清空历史撤销到"上一份数据"没有意义

最容易忽略的一条：拖一个顶点时 TerraDraw 会产生几十次 updateGapGeometry。不合并的话，拖一次就把 40 步栈填满 —— 用户按 Ctrl+Z 看到的是"边界一点点回退"，而不是"回到拖之前"。这比不能撤销更让人困惑。

4.2 框选：为什么不用 queryRenderedFeatures

问题后果
只认"当前渲染出来的"同一块地在 z14 命中、z12 因为太小没渲染就漏掉 —— 结果随缩放变
跑在 WebGL 里npm test 完全测不到
不区分类别可见性会盲删隐藏层

盲删是这一节最危险的事：默认只勾选「确定需补种」两个类别， road / water / alley_gap 是隐藏的。 如果框选遍历全部要素，一次"批量删除"就把看不见的道路水塘一起删了 —— 地图上完全看不出来（它们本来就不显示），交付包却少了 180 条道路。

所以判定抽成纯函数，强制传 visibleClasses： selectGapsInBox(features, bbox, visibleClasses)。 单测里有一条专门反证："全部可见时三个都命中 / 隐藏时只命中空地"。

交互侧还有一个 MapLibre 的坑：默认把 Shift + 拖拽 绑成 boxZoom（拉框放大）。进框选模式必须 disable dragPan 和 boxZoom， 否则用户一拖地图就缩放。

4.3 复核清单：二八定律

按面积降序 —— 前 30 个大斑块通常占 80% 的争议面积，从大到小过一遍比随机点效率高一个量级。 点一行会自动 ensureVisible(class) 再 fitBounds： 「不确定」类默认是隐藏的，不先打开就飞过去，用户会看到一片空白。

6. 生成高度图与林地边界：一行算法都不改地接进界面

换园区时 chm.tif 与 forest-mask.geojson 必须重算 —— 它们是从 DSM 派生的，不是用户准备的源文件。 这两个文件决定「多高才算树」和「哪片是未开发林」，缺了检测会静默退化成纯 RGB。 所以界面必须能做，否则换园区就只能出降级结果，而屏幕上不报错。

6.2 三个设计决定

决定为什么
不改算法脚本 两个脚本加起来几十条 log()。改写它们等于把算法文件变成 UI 的一部分（以后动算法就得考虑 UI）。做法是替换模块级引用： BC.log = my_logger —— 脚本不知道自己被包装了。
stdout 设防 宿主逐行解析 NDJSON，而 GDAL/rasterio 会往 stdout 打版本警告 → 多一行就多一条 raw 事件。用一个只放行 JSON 的 sys.stdout 守卫，其余转 stderr。实测 21 个事件 / 0 个非 JSON。
不可取消 检测可以 cancel（半成品无害），但生成中途杀掉会留下半个 CHM， 而检测读到它根本不会报错（NaN 区域变少，但仍是有效栅格）。 所以运行时把关闭按钮也禁掉 —— 半成品比没有更糟。

6.3 进度不造假精度

CHM 里那个 30 m 窗口的最小值滤波是纯计算、内部没有可插入的进度点。 所以 ratio 是按实测耗时粗估的（CHM 75% / 掩膜 25%）， 阶段内按日志行数线性推进但封顶 95%。真正让人安心的是 message（"当前在干什么"），界面上配了最近 4 行算法日志。

实测（本机，WGR17 全量）：42 秒， CHM 5891×5585 @ 26 cm/px（P50 树高 6.24 m）、掩膜 2 个多边形。

6.4 两个互锁

  • 与检测双向互斥：两者都写 output/，同时跑会互相覆盖中间产物。 所以"检测在跑"时不允许生成，反之亦然。
  • 生成完必须重跑检测：旧结果是用旧的高度图算的，直接导出会得到和新 CHM 对不上的数字，而界面上看不出任何异常。完成态文案强制写了这一句。

闭环：检测预检里缺 CHM / 掩膜时，那张卡片上直接给 「去生成高度图 / 林地边界」按钮。以前只能提示"结果会退化"——用户知道会算偏， 却不知道下一步该做什么。

7. 验证集：把「有多准」变成一个能报出去的数字

前面六章解决的是「能不能用」。这一章解决「准不准」——一个此前完全空缺的问题。 在此之前，项目里所有关于准确率的说法都是间接推理：空地距树心 2 m 内只有 2.0%（基准 14.5%）、 CHM 阈值 ±1 m 会造成 ±30,400 m² 波动。这些能说明方法可信，但没有一个数字能写进交付说明。

7.1 为什么必须抽样，而不能全判

1,726 块要人逐块判真值，按每块 10 秒算也要 5 小时，且判到后半程注意力已经崩了。 抽样 150 块（约 8.7%）能把工作量压到半小时以内，但——简单随机抽样不能直接反推全园， 因为「大块」和「不确定块」的判错率完全不同，随机抽会让 40 个 3,000 m² 的大块 和 1,400 个 50 m² 的小块获得同等代表权。

所以用分层抽样 + 逆概率权重（Horvitz–Thompson）。分层是按「判错代价」分的， 不是按类别分的 —— 这是设计上的关键选择：

层配额为什么单独成层
L1 大块（≥500 m²）40面积占大头，一块判错的面积代价等于几十块小的
L2 不确定块60算法自报 uncertain 的 465 块，是错误最集中的地方
L3 可补种25测「确定需补种」的纯度（precision）
L3 林间空隙15测「该补的有没有漏」（alley_gap 的召回）
L3 不可种植10测道路/水体/办公有没有把可补的地判死

每块的真值判定是 4 值：plant（真该补）/ not_plant （不该补，是树或硬化地）/ unsure（真值也说不清）/ missed （算法漏了）。前两个计入准确率，unsure 明确排除 —— 宁可样本变少，也不要 把"说不清"混进分子或分母，否则准确率会被稀释成一个谁都不敢用的数。

7.2 权重怎么算，以及那个"一眼自检"

层的权重  w_h = N_h / n_h        N_h = 该层总块数，n_h = 该层抽中块数
全园无偏准确率 = Σ(wᵢ · 1[判对]) / Σ(wᵢ)

因为 Σ(wᵢ) = Σ(N_h/n_h · n_h) = Σ N_h = N， 所以权重之和必须精确等于全园块数 1,726.0。这是唯一一个"看一眼就知道权重算错没有"的自检 —— 权重公式写反、层号对错、抽中块被删掉没重算，都会让这个和不成立。 实测输出 权重和 1726.0，与全园总数逐位一致。

为什么这个自检重要：加权准确率算错的典型表现是"看起来很正常"的百分比 （比如把 72% 算成 94%），人眼分辨不出来。Σw = N 是恒等式， 不成立就一定是代码错了 —— 不依赖任何真值数据就能验证，所以能放进自动化测试。

7.3 抽样必须可复现

用 mulberry32（seed = 42）而不是 Math.random()： 同一份结果文件永远抽出同一批 150 块。否则「上周判的」和「这周判的」不是同一批， 进度存下来也没法续，两次评估结果更没法比较。

实现上有一个坑值得记：initValidation 的 effect 依赖里必须包含 validation.scope 和 samples.length。 依赖太窄时 React StrictMode 的二次执行会复用旧闭包 → 重新抽样、把已有进度全抹掉， 而界面只表现为"进度 0/—"，看起来像没数据。

7.4 键盘流：为什么不是"填表"

150 块如果用鼠标点下拉框，30 分钟会变成 2 小时。所以做成 「↑↓ 换块（地图自动 fitBounds）→ 看一眼 → 1/2/3/4 打标 → 自动跳下一条」的单键流。地图飞过去这一步是省不掉的： 判真值必须看图，列表摘要不足以判断。

快捷键有四条护栏，全部抽成纯函数 shouldIgnoreHotkey() 以便单测： 带修饰键让位（Ctrl+Z 不该被当成打标）、长按重复让位、 有弹窗让位、焦点在输入框让位。前两条是这个功能特有的 —— 按住 1 不放会在一秒内把后面几十块全打成同一个值。

第一版真跑出来的错：L2 不确定块这层允许 Space 直接确认，而 Space 沿用了 "按算法类别确认"的语义 → 60 块里有 51 块被存成"存疑"（unsure）， 这一层等于白抽。一次真实运行才暴露的问题，单测里构造的数据全是"人会好好判"的理想情况。 修法：canConfirm(cls) 拦住 uncertain， Space 改为提示「请按 1/2/3 选一个真值」。

7.5 进度持久化与「真值 ≠ 复核」

每判一块立刻写 localStorage（关软件、重启电脑都不丢）。 但标注记录不与复核结果混存：复核是"改掉算法错误、影响交付"，验证是"记录算法对错、不影响交付"。 混在一起的话，用户改完一块再去看验证集，会看到自己刚改的类别被当成"真值"—— 用算法的输出去检验算法，这是自证循环。

7.6 评估脚本：三档准确率 + 一个"别把噪声当改进"的护栏

.venv/Scripts/python.exe scripts/eval_validation.py 标注.json [结果1.geojson 结果2.geojson ...]
指标含义什么时候看
样本准确率150 块里判对的比例（不加权）想知道抽样本身质量
全园无偏准确率HT 加权，代表全园 1,726 块对外报数只用这个
面积加权准确率按每块面积加权判断"错在不在大块上"

另外输出混淆矩阵（哪一类被错判成哪一类）、分层小表（哪一层最差）、 以及「确定需补种」的 precision / recall。

多结果对比时脚本会强制一项护栏：两个版本差距小于 2 个百分点时，标注为「不可区分」。 150 块样本的抽样误差本来就在这个量级，不加这条警告，任何一次参数微调都会被读成"提升"。

脚本自带 --selftest（16 项）：权重恒等式、unsure 排除、混淆矩阵行列和、单层退化、零样本不除零、合并口径三项，都在里面。已并入 scripts/check_all.py 第 7 层。

7.7 --merge-not-plant：标注口径错位时的补救

真值 4 类里，「无需补种」（2）与「不可种植」（3）的分界是算法视角的： 前者是树冠下、林间通行道那种空着但不该补，后者是路/水/房/天然林那种压根不能种。 但在正射影像上两者长得一样——都是"没树的空地"。第一份真实标注就是 88 个 1 + 62 个 3、零个 2，用户明确说分不清 2 和 3。

后果不是"标注质量差"，而是系统性冤枉算法：算法判 alley_gap （等价 gt=2）的 15 块里有 13 块被标成 3，严格口径下这一层 0%， 而它其实判对了 13 块。整体准确率因此从 88.9% 掉到 44.7%。

所以加了 --merge-not-plant：

环节处理
真值侧gt ∈ {2, 3} → 「不补」；gt = 1 仍是「补」；gt = 4 仍排除
预测侧not_needed 与 unplantable 合并成「不补」
uncertain 预测不进分子也不进分母，单列「待复核 N 块 / 权重 W」

第三行是这条设计里最要紧的一点：算法说"要人看"不是一个判断。 记它对＝把待复核桶虚报成准确；记它错＝把算法冤枉成很差。两种都会把这个数变成一个 没人敢用的数。合并后评估的是「这块该不该补」这个业务判断，而不是四分类。

为什么走独立的 evaluate_merged() 而不是给 evaluate() 加一堆 if：严格口径的每个数字（含混淆矩阵的行和列） 都必须保持逐字节不变——两个口径混在一处，最容易"改一个顺手把另一个算错"。 代价是多遍历一遍 150 块，可以忽略。实测已 diff 验证：不加参数时输出与改动前完全一致。

另有一条自检钉死权重守恒：计分权重 + 待复核权重 = 全部可评估权重。 权重丢一半时，准确率照样是个漂亮的百分数，没人看得出来。

已闭环，且结论出人意料：2026-10-19 深夜拿到第一份真实标注 （150 块全部判完），合并口径 88.9% / 77.9%。但抽样来源是桌面端当天的 1,762 块那次运行， 不是交付基线——两者差在林地掩膜 / ROI / 网格原点三处输入。 所以 702 vs 727 仍不做决定；而真值暴露出的真问题不是这 25 块， 是 ≤220 m² 的「确定需补种」约 1/3 是误判（全园投影约 231 块）。

8. 导入期金字塔体检：让"新电脑 + 新影像"不至于像卡死

前七章解决的是"装上之后能不能干活"。这一章解决一个只有在别人机器上才会暴露的问题： 你导入的影像，可能没有加速结构。

正射影像 4.7 GB、4700 万像素。缩放到远处时，程序本来只需要读一张"缩略图"； 如果影像里没有预先生成的缩略图层（金字塔 / overviews），GDAL 只能每次去原图里按比例抽样 —— 实测 z=13 一张瓦片 104 秒、z=15 35 秒。用户看到的是两分钟的全黑地图， 99% 的人会认为软件卡死并直接关掉。

为什么开发时完全没发现：项目自带的 WGR17-002.tif 在 2026-10-17 就被就地写过一次金字塔 （3.48 GB → 4.66 GB），所以本地一切正常。这个功能的价值只对"第一次用的人"存在。

8.1 检测怎么做的（比想象的简单）

不需要读像素，也不需要算 —— 打开数据集问一句就行：

with rasterio.open(path) as ds:
    levels = ds.overviews(1)   # 第 1 波段的降采样倍率
    # 有金字塔 → [2, 4, 8, 16, 32, 64]
    # 没有     → []

底层是 GDAL 读 TIFF 的元数据：金字塔要么作为 SubIFD 写在 .tif 内部，要么作为同名 .ovr 边车文件躺在旁边。两种都能被 overviews() 看到。4.7 GB 的影像读一次元数据约 0.3 秒。

8.2 三条路，和一条走不通的路

策略改源文件额外磁盘前提 / 说明
外置 .ovr否约 1/3 最理想，但需要 gdaladdo 命令行工具；本机与打包态都没有
复制副本（默认）否约 1.5 倍 无前提。副本放 output/.tile-cache/，可随时删
就地写入是，不可逆约 1.34 倍 只在 --ovr-mode inplace 时启用，界面上带红色警告

为什么不把 gdaladdo 一起打包： 它自带一套 GDAL DLL，和 rasterio 依赖的那份很容易撞版本 —— 那类问题只在冻结态暴露， 排查成本极高，而收益只是"省 1/3 磁盘"。宁可让用户复制副本，也不引入 DLL 冲突风险。

8.3 三个"不做"的决定

  • 不做进度条：gdaladdo 与 rasterio 的 build_overviews() 都没有进度回调。 画一条走到 60% 的条就是骗人 —— 只给转圈 + 已用时计时器 + 「约 2~3 分钟」的诚实预期。
  • 不做假精确的耗时：文案写「预计约 3 分钟（按影像体积粗估，实际可能更久）」， 括号里那句是刻意留的。
  • 「以后再说」不写 localStorage：只在本次会话生效。写了就等于让用户 永久关掉一个真实存在的性能问题。

8.4 两个只有在真机上才会撞见的 bug

① 防重入锁防不住"关窗重开"

原先用 AtomicBool 防连点，但它只活在本进程内存里。 用户点「开始」→ 嫌慢 → 关窗 → 重开 → 再点一次：新进程的锁是全新 false（放行），而上一轮的孤儿进程还在往同一个 .part 写 4.7 GB —— Windows 下必撞 PermissionError: [WinError 32]。

解药不是"再删一次 .part" （那只清垃圾，不消竞争），而是启动新进程前先让旧的死掉： 子进程登记进 Services 的第 4 个槽位，spawn 之前先 kill + wait，退出钩子也统一收尸。

② 复用分支漏清残留 .part

copy 模式在"副本已存在且带金字塔"时会提前 return， 根本走不到后面的清理。于是"副本已建好 + 某次中断留下半截 .part"这个组合，会把一份完整副本大小的垃圾 永久留在盘上（真机 4.7 GB）。已在 return 前补 unlink(missing_ok=True)，并加了反向验证的测试。

8.5 失败态：人话打头，原文降级

后端报错原文是「找不到 gdaladdo，无法生成外置 .ovr」—— 这句话对最终用户等于什么都没说。所以：

这台电脑缺少一个可选的加速组件          ← 人话（主文案）
可以先关掉这个提示。检测和导出都不受影响，只是地图缩放到很远处会慢一些。   ← 下一步
技术细节（反馈问题时可把这段发给技术支持）：   ← 降级为次要信息
  建立加速结构失败：找不到 gdaladdo，无法生成外置 .ovr   ← 原文，可选中复制

两者都要：人话给用户，原文给技术支持。只留人话会让排障失去唯一线索， 只留原文则等于没写。

8.6 磁盘预检里的一个坑

建副本前要先算"够不够"。第一版直接 shutil.disk_usage(cache_dir) —— 首次运行时 output/.tile-cache 还不存在，直接抛 FileNotFoundError，被兜底成 free = 0， 于是 4.7 GB 的副本被误判成"磁盘不够"，按钮永远灰着。

修法是向上找最近存在的祖先目录（同一分区，剩余空间等价），最多上溯 8 层。 这种"路径还不存在"的坑，只有真跑第一次才会撞上。

8.5 交互打磨（2026-10-22）

这一轮没有改算法，全部是"让人少犯迷糊"的改动。五个问题、五处修改：

问题改法
