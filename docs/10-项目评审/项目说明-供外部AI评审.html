Forest Gap Detection · 项目说明

油棕种植园空地检测桌面应用 · 2026-10-19 · 供外部评审 / 求改进建议

这是一个单人开发、约 6 周的行业工具：给油棕种植园找出"需要补种的空地"， 输出可直接施工的交付包。已封版并发布安装包，但我知道它离"产品"还有距离。 本文按「它是什么 → 怎么做的 → 我踩过的坑 → 目前卡在哪」组织， 最后列出我最想要外部意见的 7 个问题。

一、它解决什么问题

油棕园里总有树死了、漏种了。传统做法是人拿着平板在园区里走一遍记位置 —— 229 公顷走完要大半天，还容易漏。这个软件用无人机航拍影像自动找出全部空地， 并按种植网格算出"每棵树该补在哪"。

1.1 用户是谁

角色他关心什么软件给他什么
种植园管理者要补多少棵苗、花多少钱一页报告：确定需补种 702 块 / 309,143 m² / 约 3,691 棵
现场施工队长坑挖在哪3,691 个放样点（CSV 进手持 GPS，KML 进手机导航）
GIS / 测绘要能进 ArcGIS 出图双坐标系 Shapefile + 8 个按类别分包

1.2 一条完整的活

① 选影像（4.7 GB 正射图）
② 圈范围（可选：整幅 6 分钟 / 圈定 3 分钟）
③ 检测 → 1,726 个多边形，分 8 类
④ 复核 → 删误报、改错判（1,726 块里通常几百块要人工看）
⑤ 导出 → 21 个文件 + 一页报告

为什么检测不走 HTTP

350 秒的跑批要持续回传进度。走 HTTP 得设计轮询 / SSE / WebSocket， 还要考虑端口占用、跨域、超时重连。stdio NDJSON 只有一行一个 JSON， 进程死了立刻能感知 —— 用一条管道换掉整套通信基础设施。 只有"按需取瓦片"这一件事走 HTTP（浏览器内核只认 URL）。

2.2 技术栈与理由

选择为什么不是别的
Tauri v2（不是 Electron）安装包 67.8 MiB vs Electron 通常 150 MB+；Rust 侧能直接管子进程
React 18 + zustand（不是 Vue / Redux）zustand 的快照式撤销栈实现最直接；项目只有 33 个文件，Redux 样板太重
手写 CSS（不是 MUI / Tailwind）只有一个界面、一套深色主题；引入 UI 库反而要为覆盖样式写更多代码
Terra Draw（不是 Leaflet-Geoman）与 MapLibre GL 4 原生适配，无需额外底图适配层

三、算法核心（这是最难的部分）

输入是一张 RGB 正射影像。要回答"这一小块是不是空地"，靠三层证据叠加：

证据怎么做为什么不能只靠它
颜色 ExG = 2G−R−B，阈值取 40% 分位并夹在 40~80 跨航带曝光差 3 倍（ExG 中位 37~116）；草地 ExG 比油棕还高（159 vs 64~102）——"太绿"反而可能不是树
高度 CHM = DSM − 地面高程。≥5.2 m 一定判树，<1.2 m 一定否决，中间靠颜色 大疆 DSM 被平滑，树高系统性低估 约 40%；阈值每动 ±1 m，需补种面积变 ±3.0 万 m²
语义分割 用大疆的域外分割结果识别水体（绿水塘 RGB 判断不出来） 51% 的"非树"判定完全依赖它 —— 航拍没跑这一步，精度掉一半

3.1 一个不直观的发现

纹理标准差是判"株位空缺"与"连片空地"最有效的单一特征

实测分档：株位空缺 8~15 / 连片空地 22~26 / 油棕 39~47 / 草地 46.3。
但草地与油棕完全重叠 —— 这就是"高草 vs 幼龄油棕"至今分不开的根本原因（残缺 122,784 m²）。

四、工程上做了什么（可能值得参考的部分）

4.1 确定性自检

450 秒的跑批如果结果不可复现，"改进了"和"改坏了"就分不清。所以： 任何参数变更都进参数指纹，瓦片缓存按指纹命中；同一影像同一参数重跑， 逐位一致。

4.2 三道防"静默算错"的闸

这个项目最大的教训是：最坏的错误不是崩溃，是"看起来正常但算错"。所以：

  • 检测前预检 7 项：缺 CHM / 分割 / 掩膜时 sidecar 只回一条 warn 就照常跑完 —— 必须在点按钮之前拦掉
  • 空响应不覆盖已有数据：区分"算法自报 0 块"（可清空）与"没收到报告"（必须保留）
  • 区分「用户指定时刻」与「文件 mtime」：否则回看旧批次时会被目录里更新的文件顶掉， 而 planting_grid 跟着换 → 块数完全正确、点位整体偏移

六、我最想要的 7 个外部意见

Q1 · 算法验证路线：0 标注样本的情况下，如何低成本建立可信验证集？ 我的想法是"在 1,726 块里随机抽 200 块，人工标 4 类（真空地/误报/林间空隙/拿不准）"， 但标注本身要 2~3 人日。有没有更聪明的采样策略（active learning？按置信度分层？）， 能让人工标注量降到 1 人日以内且结论依然可信？
Q2 · 高草 vs 幼龄油棕：单期 RGB + CHM 分不开（纹理重叠）。 除了"等多时相影像"，还有别的物理信号吗？我考虑过： ① DSM 的树冠形状（幼棕榈是放射状，草是面状）；② 阴影方向一致性（种植园有固定行向）。 这两个方向值得投入吗，还是注定是噪声？
Q3 · 外部分割依赖：现在 51% 的非树判定靠大疆的 segment.tif。 如果要在本地跑一个轻量分割头（不联网、CPU 可接受、PyInstaller 能打包）， 现实吗？我的判断是"用 1,726 块人工标注做弱监督 + 小模型微调"， 但没有 GPU，也不敢引入 PyTorch（安装包会从 68 MB 涨到 500 MB+）。 有没有 CPU 友好（ONNX / 量化）的路线推荐？
Q4 · 网格对齐：全图用单一网格原点，整体对齐率只有 46%。 我在 300 m 窗口做细扫能到 79~97%，说明存在局域形变。 问题：做局域网格拟合（分块求相位再插值）会不会引入"接缝"？ 以及，有没有成熟的"周期性点阵相位恢复"算法（类似晶体学的相位展开）可以直接用？
Q5 · 架构取舍：现在是"Python 算法 + Rust 外壳 + React 前端 + stdio 管道"。 如果未来要做 Web 版（多用户、浏览器里跑），这套 sidecar 架构要怎么演进？ 我的直觉是"抽出一个任务队列 + 对象存储"，但这等于重写。 有没有更平滑的迁移路径？
Q6 · 工程质量：529 个断言、45 条坑记录、零 CI。 在单人项目里，投入产出比最高的下一件事是什么？ （CI？E2E？组件测试？类型收紧？）如果只能做一件，你选哪个，为什么？
Q7 · 产品化：现在换园区需要"文件名叫对 + 目录放对"，是隐式契约。 真正的产品化应该长什么样 —— 是"项目/工作区"概念（每个园区一个目录，带 manifest）， 还是"导入向导"（选文件时自动推断关系）？两种对现有代码的改动量差多少？
