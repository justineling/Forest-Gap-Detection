缺陷与优化清单（自检版）

Forest Gap Detection · 2026-10-19 全量自检 · P0 5 项 / P1 11 项 / P2 9 项

这份是我自己在封版前逐层翻了一遍的结论。不是"待办清单"，是带证据的缺陷台账 —— 每条都标了「怎么发现的 / 影响了谁 / 修它的成本」。 排序原则不是"技术上多难"，而是「用户会不会因此拿到错的结果还不知道」。

先说这轮已经修掉的（避免重复提）

  • 结果文件写死文件名 → 检测成功但界面全空（改为扫目录取最新 + 缓存按 mtime 失效）
  • 空响应覆盖现有 1,762 块数据（改为区分"算法自报 0 块"与"没收到报告"）
  • 网格串批次 → 块数正确但点位整体偏移（改为区分「指定时刻」与「文件 mtime」）
  • ?mock=ready 缺 bounds_wgs84 → 地图整块崩（这个坑曾让截图自检变成假绿）
  • 坑文档编号断层（37 直接跳 41）+ 三处条数引用不一致

P0 · 会让用户拿到错结果，而且看不出来

P0-1检测完不重跑也能"看起来正常"地交付
怎么发现做"生成高度图"功能时想到：用户换 CHM 后如果不重跑，报告里的株数是按旧 CHM 算的
影响已完成态文案写了"下一步：重跑检测"，但只是提示，没有阻断。用户点「知道了」就过去了
建议在结果文件里存 chm_mtime；/gaps 返回时比对当前 chm.tif 的 mtime，不一致就在状态栏挂一条橙色警示「结果是用旧的高度图算的」
成本小（半天）：Python 写 mtime，Rust 透传，前端显示
P0-2没有标注验证集 —— 所有算法改进都在盲改
怎么发现翻缺陷台账：CHM 阈值 5.2/1.2 只用 5 个真值点标定
影响任何阈值调整都无法判断"变好还是变坏"。这是整个项目的天花板
建议从 1,726 块里按"面积降序 + 置信度分层"抽 150~200 块人工标注（4 类）。
关键设计：标注界面就用桌面端现有的复核清单 —— 标"这是不是真空地"顺手就完成了，不用另做工具
成本中（2~3 人日标注）。但它是解锁 P1-3 / P1-4 / P0-1 的前置条件
P0-3生成派生数据不可取消 —— 但失败时没有任何恢复指引
怎么发现自己测"生成中途杀进程"时发现会留半个 CHM
影响断电 / 蓝屏 / 强制关机后，output/chm.tif 可能是半截文件，而检测读到它不报错 （NaN 变少但仍是有效栅格）→ 结果偏了但没人知道
建议写临时文件 chm.tif.part，成功后原子 rename；启动时若有 .part 残留就提示"上次生成中断，请重新生成"。
这是标准的 write-temp-then-rename，但现在的 build_chm.py 直接写目标路径
成本小（半天）：改 build_chm.py 与 build_forest_mask.py 的写出逻辑 + 启动时探测
P0-4"换园区"靠隐式契约，没有任何校验
怎么发现代码里 23 处 WGR17* 硬编码；用户问"我换园区要准备什么"时，答案是一堆"要放对目录"
影响换园区后如果目录结构不对，检测会静默降级（缺 CHM → 纯 RGB）。 虽然预检能提示，但预检本身也可能因为路径规则说不清而漏判
建议引入 工作区（project）概念：一个目录 = 一个园区，内含 manifest.json（影像/DSM/segment/树心表的相对路径 + 创建时间）。 打开工作区即校验，缺文件当场列表。
代价：要改 data_base() 与 settings.json 的语义
成本大（3~5 天）。但每换一次园区都能省下"为什么结果不对"的排查
P0-5同一份数据跑两次，块数会差几十块（未复现，存疑）
怎么发现对比不同时间的导出：1,726 / 1,762 / 1,751 三个数字都出现过
影响如果是真差异，说明存在未控的随机性（多进程浮点累加顺序？）—— 这会推翻"逐位可复现"的承诺
目前判断大概率不是 bug：这三次用的输入不同 （一次补掩膜前、一次补掩膜后、一次不同 CHM）。但没有一次受控的 A/B 证明过
建议做一次受控实验：同影像、同参数、--force 重跑两次， 比 summary.by_class 的每一位。这条要么变成 P0 真 bug，要么从此关闭
成本小（1 小时），但必须先做 —— 不确定性本身就有成本

P1 · 会让人困惑或返工，但不会算错

P1-1没有日志轮转 · app.log 无限增长
证据grep -n "rotate\|maxBytes" desktop/src-tauri/src/lib.rs → 零命中
影响长期使用后日志文件会到几百 MB。用户报障时也不好意思发一个大文件
建议超过 5 MB 就滚动，保留 3 份。或者只保留最近 500 行（排障只需要最后几十行）
成本很小（1 小时）
P1-2没有错误上报 —— 用户崩溃时只能手动发日志
证据全项目搜 sentry / telemetry / crash_report → 零命中
影响现场用户说"它报错了"，你只能让他去找 %LOCALAPPDATA%\fgd\logs\app.log。 而多数人找不到路径
建议不做联网上报（行业工具、内网环境）。改成 「⋯ 更多 → 导出诊断包」：打包 app.log 最后 200 行 + settings + 系统信息 + 最近一次预检结果， 生成一个 zip 让用户发过来
成本小（半天）。比接 Sentry 更适合这个场景
P1-3零 CI —— 477 个断言全靠手动跑
证据.github/workflows 不存在
影响这次连续改了两天，每次靠"我记得跑一下"。如果哪次忘了，回归会静默存在
建议最小 CI 只跑三件事：tsc --noEmit、npm test、 cargo test。e2e 那几个脚本依赖真 Chrome，做成可选 job（手动触发）
成本小（半天，含 Windows runner 上 cargo 缓存调优）
P1-4没有 React 组件测试
证据10 个测试文件全部是纯函数 / store，没有一个 .test.tsx
影响"属性 tab 只在选中时出现""帮助弹窗三入口"这类渲染条件只能靠 CDP 手工验。 而 CDP 脚本跑得慢、依赖真浏览器
建议不追求全覆盖。只给条件渲染写测试（约 8 个用例）： 右栏标签、卡片状态、弹窗开关。@testing-library/react + jsdom 即可
成本中（1~2 天，含测试环境搭建）
P1-5output/ 里有 20 个测试残留 geojson
证据ls output/*gaps*.geojson | wc -l → 20； 最新一份在 40.8 小时前，wgr17-final-gaps 排第 6
影响任何拿仓库根当 cwd 的验收都会看到 12 块而不是 1,726 块。 这次它浪费了我和 QA 各一次排查
建议把测试产物统一写进 output/_tests/，并把 output/*.geojson 里非交付的加进 .gitignore。根因是"测试直接写仓库 output/"这个约定本身不好
成本小（半天，要改几个测试脚本的输出路径）
P1-6全局 CARGO_TARGET_DIR 指向外部，与打包脚本冲突
证据本机环境变量 CARGO_TARGET_DIR=D:\forest-gap-tools\rust\target（6.98 GB）； 项目内 target/ 另有 2.5 GB
影响cargo check/test 写外部、tauri build 写项目内（脚本中和了变量）—— 两份产物，且会撞 "error deleting lock file" 警告
建议二选一：① 删掉全局变量，统一用项目内 target/； ② 文档里显式写明"所有 cargo 命令都要 env -u CARGO_TARGET_DIR"。
现在的情况是两者都没做，靠记忆
成本很小（5 分钟），但要确认 6.98 GB 里哪些还能删
P1-7NC 设计里的"帮助内容"是手写的，会随界面漂移
现状已经做了缓解：helpContent.test.ts 用 135 条断言校验 "帮助里出现的类别名 = CLASS_STYLES 的 label"
仍有的洞只有"名称"被校验了，"含义描述"没有任何校验。 比如以后把 alley_gap 的业务规则从"不补种"改成"补种"，帮助里那段话不会自动更新
建议把"是否参与补种"这类业务属性提到 CLASS_STYLES， 帮助文案从属性生成而不是手写。这样规则变了文案必然跟着变
成本中（1 天，要重构 helpContent 的生成方式）
P1-8检测进度是"瓦片数"，但用户不知道一个瓦片多大
现状显示「128 / 528 块」—— 528 是什么？每块 2048 px，约 67 m 见方
建议改成「已完成 24%（约 1.4 公顷 / 229 公顷）」，或直接「已扫过园区 24%」。 瓦片数是实现细节，不是用户的心智单位
成本很小（1 小时）。需要后端在 progress 事件里带累计面积
P1-9"排坑退让距离"改了要重新导出，但界面没说
现状左栏改退让 → 点位重算 → 但已经导出的交付包还是旧的
建议导出后如果改了退让，在「下一步」卡片上提示"退让已改，需重新导出"。 store 里记一个 lastExportClearance 即可
成本小（半天）
P1-10没有"我上次做到哪"的持久化
现状关掉软件再开，五步流程回到"复核"（因为结果已加载），但 哪些块复核过、哪些还没只在本次会话有效
影响1,726 块复核到一半下班，明天不知道从哪继续
建议把"已复核"标记落到 localStorage（按 job + gap_id 集合）。 或者更彻底：复核时写 output/<job>-reviewed.json
成本中（1 天）
P1-11导出没有"部分失败"的可见性
现状/export 返回 notes[]，前端只 pushLog
影响如果 8 个分类分包里失败了 2 个，用户看到"导出完成 21 个文件"（实际 19）， 差异只在滚动日志里
建议notes 非空时导出对话框显示黄色警示块，列出缺了什么
成本很小（2 小时）

P2 · 体验与工程债

#项说明
P2-1状态栏日志不能搜索/复制排障时想找一条 W1004，只能肉眼滚。加个"复制全部"按钮即可
P2-2没有键盘导航复核清单不能用 ↑↓ 移动、回车选中。1,726 块纯鼠标点很累
P2-3没有"撤销历史"面板只有 ↶ 3 这个数字。用户不知道撤的是什么，不敢按
P2-4影像元信息不完整状态栏只有分辨率，没有采集日期 / 航高 / 云量 —— 实际复核时会看
P2-5多选后批量改判没有预览选中 40 块改成一类，点下去才知道结果。可以 hover 预览
P2-6地图没有"回到全园"按钮飞远之后只能滚轮缩回来
P2-7sidecar.py 与 tile_server.py 共享逻辑靠复制两处都有 GeoJSON 读取与类别标签，改一处忘了另一处就分叉
P2-8Python 侧无类型检查没有 mypy / pyright。这次 mask_skip 未定义就是自己发现的（运行时报 NameError）
P2-9scripts/ 19 个文件平铺算法 / 导出 / 测试 / 打包脚本混在一起，新人不知道从哪读

如果只能做三件事

按"每单位投入能消掉多少不确定性"排

  1. P0-5 · 受控 A/B 重跑（1 小时） —— 先把"到底可不可复现"这件事钉死。 如果它是 bug，其他所有优化都白谈；如果不是，这条从此关闭，不再反复怀疑
  2. P1-3 · 最小 CI（半天） —— 477 个断言现在靠"我记得跑"。接上 CI 之后， 后面所有改动都自动有回归网，投入产出比最高
  3. P0-2 · 标注验证集（2~3 人日） —— 它是算法侧的天花板。 没有它，P1-3 的 CHM 自适应、P1-4 的局域网格都做不了； 有了它，那些都能从"猜"变成"测"

不建议现在做的

  • P0-4 工作区概念（3~5 天）：改动面大（data_base + settings + 全链路路径）。 在只有一个园区的阶段做它，等于为想象中的第二园区付钱
  • P1-4 组件测试：CDP 脚本已经能覆盖渲染条件，只是慢。等 P1-3 的 CI 建起来再补更划算
  • 任何算法调参：P0-2 完成前，改阈值只是换一个"不知道好不好的结果"

附：这次自检的方法

如果别人也想给这个项目做自检，我的顺序是（从最贵的错往下）：

  1. 先问"哪种错是用户看不出来的" —— 崩溃、白屏都不可怕，最可怕的是"数字看着正常的错" （这次的网格串批次就是这类）
  2. 查同一份数据的多个消费者：结果文件被谁读？/gaps / /export / 前端载入 各取哪些字段？要素对了但网格没对就是这么发现的
  3. 跑真实的产物，不跑 mock：我因为 mock 缺字段，把"地图崩了"当成"正常"验了一轮
  4. 验证"新代码在包里"要比 hash，不能看时间戳 —— 我因此假绿过一次
  5. 文档条数要机器数：坑编号断层是肉眼看不出来的
