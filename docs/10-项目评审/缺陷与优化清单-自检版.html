缺陷与优化清单（自检版）

Forest Gap Detection · 2026-10-19 全量自检 · P0 5 项 / P1 11 项 / P2 9 项

这份是我自己在封版前逐层翻了一遍的结论。不是"待办清单"，是带证据的缺陷台账 —— 每条都标了「怎么发现的 / 影响了谁 / 修它的成本」。 排序原则不是"技术上多难"，而是「用户会不会因此拿到错的结果还不知道」。

⚠️ 一条不成立的建议：ruff 抓不住 mask_skip 那类 bug

实测结论

评审建议用 ruff check --select F821,F823,E9 抓 "mask_skip 只在某个分支被赋值、另一分支使用"这类 bug。 实测抓不到： 

def demo(flag):
    if flag:
        v = 1
    return v        # ruff F821/F823/E9 → All checks passed

原因是这两个概念不同： undefined name（名字从没出现过）vs possibly-unbound（可能没赋过值）。 pyflakes / ruff 不做控制流分析，只能抓前者。要抓后者得上 mypy / pyright。

所以那一层补了一个成本更低但覆盖不同的检查：每个 CLI 脚本跑一次 --help。 2 秒覆盖 9 个脚本，能抓——

  • argparse 配置错误（裸 %、参数名冲突）—— 当场抓到了一个真 bug
  • 模块级导入失败
  • 参数定义处的 NameError

它抓不到"函数体内的可能未绑定"，但那类问题跑一次真实流程就会暴露， 而 --help 冒烟是零成本的——两者互补，不冲突。

受控实验结论（2026-10-19，全量 528 瓦片 × 2 次）

① workers=6 与 workers=1：8 个类别逐位一致
同一份影像、同一套参数、只改进程数，两次跑完 by_class 完全相同。 多进程的"按 tile_idx 排序后再累加"那条护栏确实有效。

② 那为什么"1,726 / 1,762 / 1,751"三个数字不同？
因为它们的输入不一样（补森林掩膜前 / 后 / 不同 CHM）。总数 1,726 其实每次都一致。

③ 但发现了一个更值得注意的事实：类别归属会随网格参数变。
交付基线（10-17）用的是网格 8.45 / 7.3179 m（origin_x 158.95）； 当前代码算出 8.35 / 7.2313 m（origin_x 159.32）—— 这是 建金字塔后的已知改进（更接近真实物理株行距）。网格变了，株位空缺/连片空地/待复核的 判定跟着变：open_patch +15、vacant_slot +10、uncertain −26，但总数仍是 1,726。

⚠️ 由此产生一个需要决策的事（不是 bug）

当前代码重新跑，会得到与已交付基线不同的类别分布（总数相同）。 也就是说：如果现在重新生成交付包，「确定需补种」会从 702 块变成 727 块 （open_patch + vacant_slot），苗木量跟着变。

这不是错误 —— 新网格更准。但它意味着： 已交付的旧数字和将来的新数字不能混用。要么保持基线不动， 要么重新生成基线并通知所有拿到旧交付包的人。这个决定需要业务侧拍板。

P0-5 的结论怎么写才准确

原来的承诺是「逐位可复现」。实测后应该改成更精确的两句话：

条件结果
同影像 + 同参数（含 workers 1 vs 6） 逐位一致（8 个类别全对得上）
同影像 + 网格参数变了（株距 8.45→8.35） 总数可能不变，但类别归属会变

所以"可复现"要限定为"同参数"，而不是笼统的"重跑结果一样"。 参数指纹里已经包含网格相关参数，所以这个限定在技术上本来就是成立的 —— 只是之前的表述没写清楚，容易被理解成"随便重跑都一样"。

  • P0-4 工作区概念（3~5 天）：改动面大（data_base + settings + 全链路路径）。 在只有一个园区的阶段做它，等于为想象中的第二园区付钱
  • P1-4 组件测试：CDP 脚本已经能覆盖渲染条件，只是慢。等 P1-3 的 CI 建起来再补更划算
  • 任何算法调参：P0-2 完成前，改阈值只是换一个"不知道好不好的结果"

附：这次自检的方法

如果别人也想给这个项目做自检，我的顺序是（从最贵的错往下）：

  1. 先问"哪种错是用户看不出来的" —— 崩溃、白屏都不可怕，最可怕的是"数字看着正常的错" （这次的网格串批次就是这类）
  2. 查同一份数据的多个消费者：结果文件被谁读？/gaps / /export / 前端载入 各取哪些字段？要素对了但网格没对就是这么发现的
  3. 跑真实的产物，不跑 mock：我因为 mock 缺字段，把"地图崩了"当成"正常"验了一轮
  4. 验证"新代码在包里"要比 hash，不能看时间戳 —— 我因此假绿过一次
  5. 文档条数要机器数：坑编号断层是肉眼看不出来的
